## 验收

### A. 请求模型与力度：先有取证入口，再补实际调用

1. 使用当前 reasonix run 正式入口及现有受支持配置/帮助/诊断。先核对本次用的是哪个可执行文件、版本、profile、工作目录及参数优先级。仅记录非敏感字段，不读取被拒绝的受保护目录、不打印凭据。
2. 复用原允许的任务回执，区分：
   - configured：配置默认值；
   - requested：本次路由或CLI意图；
   - sent：真实序列化发送参数；
   - reported：供应商实际返回的标识。
   四层不能相互冒充。没有供应商reported字段不自动否定已有sent证据；有CLI参数也不自动证明sent。
3. 配置与旧快照不同时，先列出非敏感差异和适用时间，不为让旧证据“对上”而回退配置。旧结果仅在版本、入口、参数前提相符时复用。
4. 优先用当前已有官方诊断或脱敏请求回执关联 task_id/session_id/request_id 与 sent_model、sent_effort、入口版本。若现有官方请求构造代码可安全读取，可作映射依据；只读代码证明映射，仍需运行记录证明该请求实际发生。
5. 不新建代理、不拦截TLS、不导出浏览器cookie、不抓取未授权会话。若已有诊断只会记录原始密钥/完整敏感请求，则不用该入口；不能为取证扩大收集范围。
6. 若已确认有可用取证入口，把“两模型、同模型两档”的调用尽量嵌入后续20次独立任务；保留原失败任务的最小复测，避免为了每个字段另开任务。当前可用名称从实际入口获取，不硬编码历史模型。
7. 若证据证明任务级参数确实传错、被已有配置覆盖或需按官方格式转换，优先恢复现有正确调用方式。只有确认既有任务适配存在缺陷时，备份后最小修正该适配并回归；不改供应商、密钥、Reasonix全局配置或另造执行器。
8. 找不到允许的sent证据时，记录 PARAMETER_EVIDENCE=EVIDENCE_GAP；业务任务和其他验收继续。不得先重跑一批相同调用，最后仍只得到同样UNKNOWN。
通过条件：两个当前可用模型及同模型两种支持力度都有可关联实际发送证据；实际声明的其他档位至少有明确映射/支持范围。只测两档不得写全部档位实调用通过。

### B. EXTREME极限档：区分路由档位和执行强度

1. 读取现有四档合同；EXTREME 是任务质量等级，MAX 是抽象强度要求，不假定所有宿主都有字面max参数。若宿主采用不同枚举，必须用该版本官方已有映射说明；缺少映射不能自行宣布等效。
2. 采用现有隔离多文件修复案例，或成熟测试夹具中的强耦合问题：有明确依赖、至少两项相互约束的成果及独立可执行断言。通过输入约束和真实错误代价体现复杂度；不因长提示词自动升档，不制造真实高风险外部动作。
3. 完成一项明确指定极限档的任务和一项不透露期望档位、符合原EXTREME定义的任务，分别验证遵从指定与自然路由。明确指定不可用时可报告最接近可用路线，但不得把降档记作原EXTREME执行通过。
