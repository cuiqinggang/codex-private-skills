# 原单停滞后的接管与签收

遇到执行器退出、重试耗尽或任务长时间没有业务进度，按本页处理。执行者持有原步骤的写入权，环外接管者持有修复和对账责任。保持两者的责任记录，直到独立签收、用户取消或原合同明确终止。

## 先确定输在哪里

读原合同、任务键、Workflow ID、Run ID、步骤/轮次、请求摘要、原队列和最后一次已验收的业务结果。同时查正在执行的 Activity、待触发的计时器、发单器和看门狗。分别报告已受理、正在执行、已交付和已独立验收的数量。按原合同分别计量首波耗时、耐力观测时长及包含修复等待的端到端耗时。

## 按证据选择下一步

| 本次可核实的事实 | 接管者现在执行的动作 | 下一次唤醒依据 |
|---|---|---|
| 本地临时故障，权威订单状态已提交 | 修复失败的本地步骤。按订单去重，从权威状态重建派生汇总。对短时 Windows 文件共享冲突有界退避，保留原子替换；长期拒绝或磁盘错误如实报告 | 重新读回原状态、账本、汇总及唯一业务键 |
| 供应商结果迟到，能与原请求和原 Run 精确关联 | 核验原始成功结果、实际路线、产物与哈希，按原键一次性补入业务检查点。已有相同检查点可复用，不同内容转冲突。费用单独待核，按首波合同决定何时签收 | 原始成功回执或可独立核验的新业务证据 |
| 供应商打印超时、输出为空或进程失联 | 保全原键、已确认的会话标识、原始输出字节数/哈希、实际退出或超时信息。按供应商支持的只读渠道查原请求。零 token、空文件及额度面板均不足以认定未发送或零费用 | 原请求有可归属的最终结果、权威未受理证明，或收到原合同授权的补偿裁决 |
| 权威记录证明从未受理，原动作允许再次提交 | 核验原授权、预算、旧写入者和动作键；从第一个未完成动作继续。结果未知时禁止重新提交有副作用或可能重复计费的请求 | 新结果与原业务键匹配 |
| 原单对账成功、后续阶段仍受权限或模型入口限制 | 接管者先补已证实的本地业务检查点。仅在后续动作获准且原执行器能按预期停靠时才唤醒原 Run；独立订单及不依赖该动作的已授权步骤继续 | 已验证的后续入口及匹配当前阶段的原生接续条件 |

## 重试耗尽后的责任

1. 给每笔待核原单保留接管者、待核依赖、上次证据指纹、下一次检查时间或事件、以及有证据时可执行的具体动作。复用现有监督任务。监督器退出前核实该任务已登记且可运行；没有接管者时将缺口报给任务负责人。
2. 到期回查原服务和原单证据。相同指纹只更新巡检状态。证据有变化时立即按上表处置；读回检查点证明修复生效。信号是否送达未知时先查原生历史。用原 Run、步骤、轮次、当前序号和证据指纹去重。
3. 有持续执行的原 Run 时保留其写入权。整条恢复信号可能释放多个下游动作，先核清边界。已验证的修复可放入下一进程版本，运行中的 Worker 是否加载新代码另行取证。
4. 对每次修复记录触发故障、修正、验证结果和业务推进量。至少用“临时故障后成功”“永久故障仍失败”“重复观测仅收一份”三个反例检查适用修法。重启次数、测试通过数及监控在线用于诊断；以新增的已验业务步骤或交付衡量推进。

## 区分进程故障与业务待核

- 子进程正常返回待核退出码，且原状态与汇总匹配、每笔未完订单均可归属原 Run 及明确的规划关口时，交给已登记的独立接管者查原证据，保留已有重启计数。心跳过期、进程异常退出、RPC 失败或状态与汇总冲突时，沿用有界基础设施恢复。保存原始错误日志。成功读到当前原生停点后，从当前订单状态移除旧 RPC 错误。
- 准入截止只约束新增订单。到期后重连已受理的原单，先读终态或立即查询当前停点，为对账查询留出独立窗口。查到新证据才处理原检查点。核对当前阶段的权威序号及下一步执行权限，取得原生接续回执再登记推进。
- 优先确认下一次由谁查、什么证据能推进、到时执行哪个原动作。可独立的订单继续执行。共享供应商在同一阶段阻断全部订单时，保持原业务键可恢复，并在获准切换前验证备用入口能提供同合同的实际模型及原始回执。

## 已验证案例

2026-11-28，<HISTORICAL_BATCH_01> 的三个独立 Run 在首波 Google 规划等待原始回执。登记到看门狗耗尽恢复机会约 6 分 10 秒。账务单留下 print_timeout 和原会话标识，另外两单的原始输出为 0 字节。三个 Run 保留，交付 0/3，首波资格和后续 60 分钟实跑均未达成。用户账单与费用仍待核。

现场落地并离线验证三项修正。Windows 短时文件占用按原子替换有界恢复，20 项通过；Google 失败诊断保留本机可证实的字段和未知费用，16 项通过；终审活动的外层预算覆盖排队、执行和收尾，3 项通过并回放旧历史。排队 960 秒、执行 390 秒、收尾 90 秒为这次合同的参数，其他任务按各自实际组件重新核算。复核数据保存在原项目的 s4-evidence/endurance/live/<HISTORICAL_BATCH_01> 和 s4-evidence/<批次审计目录>。

在 PER 脚手架中，先运行 `python -B reconcile_google_plans.py --run-tag 原批次 --check-only`。遇到 `READY_TO_RECOVER` 时，沿同一命令去掉 `--check-only` 补入已验证的原 Google 业务检查点并回读。识别 `INCOMPLETE`、`CONFLICT`、`EXISTS` 与 `GOOGLE_CHECKPOINT_RECOVERED`；分别统计检查点、待核费用和正式交付。该入口只查本地规划回执，不发模型请求，不发送恢复信号。

对本案有原供应商会话 ID 的订单，官方只读会话加载返回过零条重放消息。零条重放只说明该次未取得可签收的正文，保留同一 ID 以供新证据出现时复查。
