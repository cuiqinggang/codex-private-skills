# Windows 增强 Pi 直投 Temporal

正式长测先执行[正式派发及验收流程](formal-run.md)。其派发程序在实际增强 Pi 身份下复查冻结计划，并调用下述原生批处理一次。已有命令包回放保留原执行和原签收。

1. **宿主就绪**。使用已就绪的 Temporal 服务和单独运行的 Worker。绑定本轮任务目录、命名空间、Workflow 类型和任务队列。派工前从原生接口确认目标队列有 Worker，并核对注册的流程和 Activity。目录存放任务文件，Worker 是执行进程。根据阶段配方，Worker 可调用 Pi。
2. **冻结一个命令包**。包内放任务清单、业务输入、CLI 输入 JSON、只读预检与提交批处理。沿用目标 Worker 的输入结构。已验短测用 `DurablePiJob`，输入为 `task_id` 和 `request_sha256`。分阶段 `DurablePiStagedJob` 需按其 Worker 实际合同验证输入与阶段回执。
3. **从增强 Pi 单次投递**。通过用户日常入口运行命令包，同一 CLI、身份、地址与命名空间先执行 `operator namespace describe`。把预检和提交串在一个批处理中，预检失败立即返回。经 Pi 的 Bash 调用 CMD 时优先使用工作区内相对文件名，避免未引用的 Windows 反斜杠被转义。用本机 `workflow start --help` 核实参数。提交采用固定 Workflow ID、`--id-reuse-policy RejectDuplicate --id-conflict-policy Fail`，记录原生 Workflow ID 和 Run ID。提交响应不明时按原 ID 查询确认。提交命令完成后，Worker 独立执行。
4. **只读观察**。以原 Run 的阶段、心跳、尝试次数与回执记录进度。查询失败显示观测失联和最后有效时间。宿主服务管理入口独占启停。监控入口只提供读权限，无服务启停或任务取消能力。故障验收由专用操作作用于该次隔离 Run 对应的目标进程。
5. **业务签收**。核对同一 Run 的原生终态、独立业务回执、产物指纹及写入次数。原生 FAILED 判整轮失败。任何短测、组件测试或终态后的诊断只支撑各自范围。

## V1.9 分阶段命令包冻结验收

1. 生成独立任务目录。将业务输入、阶段程序、阶段顺序、各阶段签收及最终回执路径写入清单。记录输入和程序 SHA-256。
2. 根据实际 Worker 生成 CLI 输入。分阶段结构为 `{"identity":{"task_id":"…","request_sha256":"…"},"stages":["…"]}`。从最终清单原始字节计算散列。使用实际安装的 Worker 构造 Job，核对输入对象、队列与固定 Workflow ID。
3. 把同身份预检与单次提交写入同一批处理。冻结时校对 Workflow 类型、ID、队列和 CLI 参数。
4. 在隔离副本执行实际阶段程序，用实际 Worker 的回执校验器核对各阶段和最终产物。篡改测试产物，确认校验器拒绝。冻结目录保持空白运行状态。
5. 写出 `FREEZE-VERIFICATION.json`，登记任务号、Workflow ID、检查项和全部命令包文件 SHA-256。第 3 步派发前重算并比对，再用同一批处理实测 Pi 预检和唯一提交。

Windows 实测 `<HISTORICAL_TASK_02>` 第 2 步 PASS。两阶段回执通过，改动产物被拒。以上为派发前冻结证据。实际队列在线及 Pi 提交另在下节签收。

## V1.10 分阶段命令包由增强 Pi 实际投递

1. 重算命令包 SHA-256，与冻结回执逐件比对。核实目录没有阶段启动标记，再启动本轮独立宿主服务。用 `task-queue describe` 核对指定 Worker 已轮询目标队列。
2. 从增强 Pi 的日常入口投递，限定当前工作区。调用 `cmd.exe /d /c submit.cmd <地址> <命名空间>`。预检级联在同一批处理内，非零立即退出。提交后从 Pi 工具日志读取真正的 Workflow ID 和 Run ID。
3. 从 Temporal 原生接口读回相同 Run，并核对两个完成标记、最终 PASS 回执与产物 SHA-256。Windows 实测 `<HISTORICAL_TASK_02>`，Run `<RUN_OR_SESSION_ID_18>` 为 COMPLETED，verify、audit 两阶段均完成，最终指纹一致。此证据覆盖正常分阶段短测。

- Reality 验收总控台（原始链接内部留存）按冻结、派工、执行、独立审核、签收展示证据。顶部显示当前真实节点，节点内显示状态、最新回执和日志。分别记录最近读取和最后一次业务进展时间。只有同一 Run 的真实阶段事件或回执可推动节点切换。读取失败显示观测失联并保留最后有效证据，恢复后回查原 Run。观察页按需打开，持久证据在宿主记录。

- 一小时 Louez 正常业务长测使用全新任务号、冻结包、独立业务数据和单次增强 Pi 派工。派工前确认实际 Worker、GUI、独立 QA 入口与回执字段连通。冻结真实预订、取还、分笔收退、相邻订单和导出对账。按原 Run 独立核对账目、写入次数、GUI 回执与产物指纹。记录实际工作量和从增强 Pi 接单到最终独立签收的完整时间。一小时用于定义测试规模，禁止用空等待凑时或作为任务强制截止。原生 FAILED 记整轮失败，后续诊断不替换该轮回执。R143 短测证据不计入长测签收。

## V1.12 R144 长测复盘与派工前复验

R144 使用全新 Louez 实例与增强 Pi 直投。原 Run `<RUN_OR_SESSION_ID_19>` 经过安装、部署、构建、冷启动和 G00–G12，随后在独立账本阶段原生 FAILED。从首次接单到原生终态耗时 43:45:917，无合格 T_VALID。备份还原与最终独立签收未执行。宿主观察记录了真实阶段切换，Sites 动态推进未签收。

G12 的 GPT 发送调用超时。Pi 用原会话和唯一标记回查，读回裁决后在原 Louez 标签完成相邻订单。之后只读数据库复核确认两单、五笔收退全部属于主单，相邻订单零付款。

根因是 GUI 回执把界面编号填进 `main_order_id` 和 `adjacent_order_id`，实际内部 ID 另存其他字段。GUI 校验只检查两个字段有差异，冻结测试又仅使用理想输入，因此错误直到下游账本才暴露。下一轮先冻结字段语义和完整样例，明确 ID 字段必须是订单详情 URL 与数据库一致的内部 ID，展示编号单独保存。生成者、GUI 关口、账本和最终 QA 复用同一字段校验。冻结时用实际生成形态验通完整链路，加入编号误填、ID 不匹配和缺步反例。GUI 关口在业务已存在时只允许修正回执和复核原账目。已终态失败的旧轮只读保全，诊断结果单列。
