# 正式派发及验收流程

## 每个新 Run 共用一条流程

| 节点 | 必须读回的证据 | 条件未满足时 |
| --- | --- | --- |
| 冻结 | 任务号、业务键、调度器、场景、入口模式、实际身份、部署配置、业务输入和验收程序的指纹 | 只补当前缺项，保持原任务记录 |
| 派发前检查 | 从实际增强 Pi 入口执行派发程序，验证同一身份、短工作区、目标调度入口、阶段接续和观测恢复 | 停在具体失败项。共享服务的其他工作流继续 |
| 原生受理 | 一次提交意图及原生回执。Temporal 核对 Workflow ID 和 Run ID。Conductor 核对原生 Workflow ID，故障轮再绑定任务和首次租约 | 回执不明先按原身份只读查账 |
| 执行、注入与接续 | 当前关卡、原进程或完整进程树、已发生业务、已验证阶段回执。注入前确认隔离范围、原生身份和冻结的业务边界 | 依回执接管原阶段。实际状态未明时保留现场 |
| 独立验收 | 同一原生 Run 成功终态、可见 GUI 步骤、账本唯一写入、审计回执与产物指纹 | 原生失败保留原终态，迟到结果用于诊断 |

每项用本轮证据推进。正常轮先证明新接线能跑通真实安装、部署、构建、GUI 和签收。已经在同一正式入口、同一软件版本和负载条件下签收过的隔离轮可以并行。共享浏览器会话或共享调度服务按实际冲突范围排队。

在同一个任务登记范围内原子绑定任务号、请求指纹和原工作流位置。同号同内容返回原结果，同号异内容保持原记录并报冲突。跨目录或端点变化先查原登记。Temporal 对照运行中冲突策略和终态 RejectDuplicate。Conductor 按当前部署核实原生幂等能力与适用范围。独立数据库各自维护登记。已生效的业务动作沿原业务键、唯一约束或原子条件写入核对。并发控制只覆盖实际冲突的资源。

R158 已用桌面增强 Pi 入口做短测签收。证据为 Windows 工作区 `r158-official-pi-entry-smoke/STATUS.json`，Run `<RUN_OR_SESSION_ID_15>`。新接线与该历史入口分开核验。验收矩阵覆盖正常交付、同号跨目录并发、同号异内容、终态重交、不同实例真实 GUI 并行、Worker 写后回执前中断、调度重启、GPT 回执丢失及独立验收反例。

## Pi 接管回执与成果报告

- 从桌面增强 Pi 的原入口接续。核对原任务和有效执行者后，把任务号、请求指纹、适用的原生工作流与 Run ID、Pi 会话、首个待验关口和已验回执写入原任务目录的持久回执。复用现有状态文件和原子写入机制。由独立读回确认接管。进程启动、退出码、空 `.claim` 或空日志只能作为诊断线索。持续接管还需核实 Pi 正在推进，或已由原调度器登记等待并具备可读回的恢复触发。
- 依赖暂不可用时，把具体探测结果、最后已验关口、原检查点和恢复条件持久记录在原任务中，单独标明已核实的执行者或仍待接续。原 Pi 已退出时，先确认原进程和在途动作，核对既有回执和账本，再由原增强 Pi 入口从断点接回。接续请求按原任务去重，原 Worker 保有业务写入权。
- 按路报告业务签收数、已完成且可复核的成果、最近明确的未验关口以及接续归属。准备、派发和只读预检可列为已完成节点。业务签收以真实 GUI、唯一账本、隔离还原、独立回执和原生成功终态为准。仅将已签收且场景相同的完整 T_VALID 纳入排名。

## 冻结和执行派发程序

1. 把批准过的配方记录为一份 JSON 计划，固定实际入口、工作目录、每项探测的参数和现成原生提交命令。使用版本固定的探测程序和输入 SHA-256。用实际入口核对访问身份和能力。临时写测试只在隔离工作区内创建自有探针。
2. 由宿主读取 Docker 引擎、目标容器、实际绑定和应用健康。把经核验的回环端点作为冻结输入交给增强 Pi，Pi 在其实际身份下探测该端点。原生 Temporal 复用命名空间与实际 Worker/任务队列检查。Conductor 复用原生健康和工作流读回。应用或端口身份变化时重取证据。
3. 可先在同一入口运行 `admission_gate.py check --plan <计划路径> --sha256 <计划指纹>`。正式派发在同一入口与计划目录运行 `admission_gate.py run --plan <计划路径> --sha256 <计划指纹>`，由程序重做检查并调用冻结的提交命令一次。使用已验过的 Windows 原生投递批处理。原生受理由独立读回确认。原提交状态未知时，按同一个任务键、目标和工作流查证。
4. 原生工作流启动后，由独立观测持续更新最后有效时间。查询错误显示观测失联，保留最后可信状态，并用原标识恢复查询。故障注入控制独立绑定该轮流程，监控失联时暂停依赖观测证据的注入。

### 计划与回执格式

- 计划固定 `schema_version: 1`、`task_id`、`scheduler`、`scenario`、`route`、`role: pi_submitter`、绝对 `work_directory`、`workflow_id`、`request`、`inputs`、`probes` 和 `submit`。场景取 `normal`、`worker` 或 `scheduler_restart`。Conductor 的计划 `workflow_id` 存固定工作流名称，调度器返回的实际 Workflow ID 另行读回。
- `request` 与 `inputs` 按 `path`、`sha256` 绑定。每个探测和提交使用 argv 数组，冻结它的源文件以及被调用的业务、探测与提交文件。需要检查 Windows 源包路径时，`archive_path_budget` 提供已冻结的 `archive`、工作区内的 `destination` 和实际工具使用的 `limit`。
- 探测顺序为 `route_identity`、`work_directory`、`scheduler_reachability`、`stage_recovery`、`readback_recovery`。故障轮再执行 `fault_prerequisite`。探测从同一执行身份运行，使用 `ADMISSION_*` 环境字段关联本次调用及冻结计划，打印一次结构化 JSON，包含关联字段和对应的 `checks`、`evidence`。字段详见脚本中的 `CHECKS`。证据引用实际标识、只读回执或可验证文件指纹。进程权限按实际工具测试。阶段及读回能力可引用同入口、版本和负载的已验证回执，探测负责重新读回和校验其适用性。
- `run` 以独占方式写入 `ADMISSION-INTENT.json` 后运行冻结提交命令。保留现有任务登记和调度器去重。独立观察按冻结目标读回真实原生身份，再登记受理。即使本地命令返回成功，`SUBMIT_RETURNED` 仍要等待原生读回。提交状态不明时保留意图，回查同一个任务，避免从另一目录或入口重交。

### 必验能力

- **实际入口和工作区**。验证精确入口模式、提交进程身份和目标目录。同一目录实测需要的工具写入能力，核对源码压缩包展开后的最长路径及构建输出目录。普通宿主线程的写入成功只能证明该宿主身份有权限。
- **阶段接续**。验证服务端收到的心跳与工作负载中可观察的心跳间隔。冻结监测范围和所需裕量。取消时确认整棵进程树的退出，或按既定契约接回原执行者。原阶段回执缺失时，用原身份核对仍存活的进程、已有产物和已提交业务，再决定接续。通过测试重放迟到回执和错误身份。
- **原 Run 读回**。让只读观测经历一次失联并恢复，核对原 Run、最近一次有效观察、变化事件和真实终态。页面刷新时间与最后一次成功读回分别记录。
- **故障轮前置**。只允许冻结的故障边界。共享 Conductor 重启须读回其他同服务轮的原生终态及独立签收，并核实只剩当前流程。Worker 注入须核对进程身份、原 Run 和阶段回执。G12 写后恢复须核实可见订单、账本和未确认回执，再注入故障，随后核回原订单及唯一写入。

## R162 回归用例

| 已证实的失败 | 改版后复验 |
| --- | --- |
| 深目录解压失败，短路径仍有实际进程写入拒绝 | 用原路径和受限身份分别跑负例。短 DSH 正例要由相同工具身份创建和清理隔离输出 |
| 宿主 Docker 可读，增强 Pi 提交时命名管道被拒 | 用原入口退出码 1 回放并确认没有触发提交。正例须从实际 Pi 读取由宿主核过的目标回环端点 |
| Temporal 心跳超时后，原部署或构建后代进程继续并产生迟到结果 | 在同负载下验证服务端心跳裕量，独立核对完整进程树及原阶段结果，触发重复尝试时保持唯一执行，旧失败 Run 保留终态 |
| 控制器查询异常退出，总控台保留旧 RUNNING | 断开观测再恢复，页面要能读回原 Run 的失败终态，并保留最近一次有效观测时间 |
| Conductor Worker 无原生回执，重启轮挂起 | 确认两轮都无原生提交，显示具体上游阻塞。放行正例需前置签收及共享服务空闲 |

R159 短测证据可复用于调度部件。R162 原生历史及迟到产物用于回归反例。新版入口必须在本机读回实际加载指纹，并完成一次真实正常长测与独立 GUI 签收后，才能登记为已验证的正式配方。
