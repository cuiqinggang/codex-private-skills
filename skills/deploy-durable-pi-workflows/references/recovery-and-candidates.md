# 修正责任和备选验证

## 谁修正，谁签收

| 失败类型 | 修正责任 | 验收 |
|---|---|---|
| 执行进程退出、回执未送达 | 调度器接管已验证可恢复的故障。执行器读原任务、会话和业务回执，确认已生效动作后从未完成节点接续 | 独立验收核对原任务身份、故障点、恢复动作及业务写入唯一 |
| 界面操作偏离要求、输出不合格 | 独立验收标记失败并提供失败项和证据。GPT 按原合同判定可保留结果、修正动作和复验范围，派执行修正。已违规的整轮保留失败记录，必要时用新隔离数据重验 | 独立验收复核真实界面、单次导出、文件和全部合同项。记录裁决是否由当班 GPT 会话提供 |
| 写入结果未知或纠正能力缺失 | 调度器保留待裁决状态。恢复责任方先读回业务账本和界面，确认写入结果后再续跑 | 验证无重复操作。未获得裁决或独立验收时继续标记待处理 |

第 76 轮 Conductor 界面 15/15、03:34.117，证明 GPT 给出修正后派能够重新跑通界面；本轮由实际 GPT 会话发出修正。无人值守的发现、派发裁决、同任务恢复及重新签收必须用同一故障注入实测，当前未验。业务完成时间从首次接单计到最终独立签收，恢复和返工计入。

## DBOS 隔离短测

本机已有 Python 3.13.12 和本地 PostgreSQL 16 镜像，未安装 DBOS。先固定官方快速入门使用的可用版本、包和数据库镜像摘要，使用独立 Python 环境和独立数据库。按官方三步样例跑一次正常结束，再在第一步已留下持久回执后停止执行进程，重启同一程序，验证相同工作流编号、只执行未完成步骤和最终签收。下一轮在实际业务写入后、步骤回执提交前停止，独立查账验证同一业务编号只写一次，再接入增强派命令行。单机重启恢复、进程监督自动重启和跨机接管分别取证。短测通过后进入同一租赁预约任务和真实浏览器界面。来源：[官方快速入门](https://docs.dbos.dev/quickstart)、[恢复说明](https://docs.dbos.dev/production/workflow-recovery)。

## ECC 与 Matt 的快速对照

- 同一增强派命令行、同一任务入口、固定源码与初始数据、相同浏览器和独立验收，测试前分别证明入口和环境可用。沿官方方法选择一个可独立交付的小改动，再上租赁预约长任务。
- Matt 复用作者公开方法：需求澄清并沉淀术语与决策、拆成可验收工单、按测试反馈实施、审查并按真实界面签收。作者教程和第三方操作指南用于核对步骤；收藏数与分支数仅说明关注和参与信号。固定历史版本后核查该版本实际包含的步骤。来源：[作者仓库](https://github.com/mattpocock/skills)、[第三方操作指南](https://github.com/adairo/mattpocock-skills-cheatsheet)。
- ECC 固定自有 3.1.1 和实际入口。历史上游 ECC 2.2.3 数据按原身份保留。已有 F015 自有 ECC 与 Matt 两组均构建通过，宿主验收失败，真实界面未运行，均无完整合格时间。ECC 3.1.2 两组暂停时均无构建检查点或独立验收派发，单独记录。
- 调度接管能力用 Temporal、Conductor、DBOS 比较。开发交付方法用 ECC、Matt 比较。若比较整条系统速度，固定同一增强派、业务任务、故障和独立验收，再按完整合格时间排序。
