# AI 化组织 V3.0 | 任务开头大号复制按钮规范

状态：V3 增量约定，保持 V2 DSH/ECC/节点版本化不变。

1. 对需要跨节点、持久化和跨聊天恢复的任务，先建立在线 N000 根索引；确认仓库写入成功，再将完整编号 `<TASK_ID>/N000/V1` 显示在首段，右侧放大号“复制”按钮。
2. 按钮约 145×108 px 起步，文字约 40 px；每次点击复制同一完整编号，颜色明显变深约 650 ms，然后自动回到原色；按钮始终只显示“复制”，每次可再次触发。剪贴板成功不能单靠变色认定。
3. 任何 N00X 具体节点也可复制相同格式的完整编号；新页面从根索引定位整个任务，从被指定节点查看合同和最新检查点，再继承此前有效回执。N000 是整个任务的索引，N001 起是业务节点。
4. 每次已确认业务节点提交后更新有效回执与 N000 最近进度。根索引可能滞后时应对账；UNKNOWN 和不可逆动作禁止盲目重做。
5. 单编号恢复的前提是新页面能通过已授权的 GitHub/C 盘工具读取对应文件。无法读取应报告 BLOCKED；不依赖坏页面重新生成恢复包。
6. 用户认可的 UI 可以在有渲染支持的响应中展示，但不能保证 ChatGPT 所有未来聊天自动配置；以每任务首次回复执行检查为准。

7. 固定 C 盘共享恢复工作区为 `C:\AI\AIORG-Shared`。新页面使用完整编号，直接解析 TASK_ID 并读取 `C:\AI\AIORG-Shared\tasks\<TASK_ID>\N000.json`，注册表位于 `C:\AI\AIORG-Shared\registry\tasks.json`；不可把任意工作区全文搜索当成默认入口。在线主仓相同任务位置为 `tasks/<TASK_ID>/N000.json`。新任务开头必须建立两端可读的 N000 后再标记恢复入口 READY，任一端失败则记录单边状态，避免虚报双端完成。

8. 复制编号仅为页面故障、卡死、无法继续时的备用恢复入口，不是正常节点切换步骤。任务开始时显示编号及大号复制按钮以便提前备用；正常页面自动连续执行后续节点并持久化，直到最终 QA 和任务完成，不需要用户逐节点复制/换页。TASK_COMPLETE 时不再要求复制或开启新页面。中间节点跨页恢复仅作为专项验收或实际故障时执行；保持 V2 DSH/ECC/节点版本机制不变。

9. 主动换页上限（2026-10-23增量）：在当前页面正常执行时，以最多 3 个业务节点作为保守上限；每节点确认提交回执，达到上限后先校验 N000 索引和下一节点，再通过官方支持的新页面入口继续，不能绕过平台限制。已完成任务不换页；未满 3 个节点即卡顿则立即故障恢复；过大节点允许更早检查点/换页。此为降低卡顿风险的操作规则，不宣称已实测证明 3 节点一定优于其他上限。主任务 T_VALID 必须计入换页、检索与恢复成本；待相同业务 A/B 后再调整阈值。过去每页≤3问与本次≤3业务节点不同，不混为一谈。复制编号是换页的恢复入口，非正常节点间逐次手动复制要求。

10. 自适应页面负荷（覆盖此前“每页最多3个节点”的保守试行上限）：按节点实际耗时、上下文、页面响应和失败/恢复代价决定继续或主动换页，不能单纯按节点个数判断；短任务正常一页完成，复杂节点可提前保存检查点。对于用户明确要求的每个新任务，开始即创建唯一编号及可靠的 N000 可查询记录，显示右侧大号可重复复制按钮；长任务每个已确认里程碑保存，出现迟滞立即考虑续页。新页面只凭编号的恢复必须以仓库或本地真实可读取的回执为依据，不能依赖未保存的“短期记忆”推断。未做真实 ChatGPT 页面 A/B 时，不称3节点或任一上限最佳。保留 V2 DSH、ECC、节点版本机制。
