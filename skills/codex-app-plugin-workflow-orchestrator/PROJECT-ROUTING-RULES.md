# Project Routing Rules

## AI Company Dashboard / Obsidian Dashboard

Preferred route:

Product Design -> Build Web Apps -> Browser or Chrome validation -> Visual Proof Acceptance.

Use this for dashboards, clickable indexes, review pages, project maps, and AI Company operating system screens.

## Screenshot or Image to Page

Preferred route:

Design input -> Build Web Apps -> screenshot comparison -> visual acceptance page.

Use exact browser screenshots when visual fidelity matters.

## Figma to Code

Preferred route:

Figma capability check -> Figma frame inspection -> Build Web Apps -> Browser or Chrome validation.

Only use real Figma access after the user provides the link and any needed authorization.

## Database / Account / Backend Work

Preferred route:

Supabase planning only -> schema draft -> local review -> explicit user authorization before any real connection.

Never mutate cloud data, auth rules, RLS policies, tokens, or production resources without a separate approval.

## GitHub Issue / PR Work

Preferred route:

GitHub read-only check -> summarize -> propose patch -> local verification -> explicit permission before remote writes.

Ask before creating issues, commenting, pushing branches, opening PRs, merging, or modifying repository settings.

## Deployment

Preferred route:

Local build -> local browser proof -> deployment plan -> explicit user approval -> deploy -> hosted proof.

Do not publish public URLs or connect project accounts without authorization.

## Complex Debug or Delivery Closure

Preferred route:

Plan -> reproduce -> narrow cause -> patch -> test -> visual proof if user-facing -> deployment report.
