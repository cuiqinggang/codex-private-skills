# 成熟复刻四列法

当任务是复刻公开但不完整的成熟方案、组合成熟组件、修复已验收系统，或补齐未知步骤时，先回归原成熟体系，再考虑新增实现。

## 开始前：冻结成熟基线

记录并冻结：原目标、来源与版本、正式入口、关键参数和约束、验收标准、已通过能力、禁止改动范围，以及未知边界。没有直接证据的“成熟能力”必须标为 `UNVERIFIED`。

## 每个缺口一行，严格按四列填写

1. **当前成熟能力**：原方案已证明具备什么、在何版本/入口/配置中成立，以及本轮冻结什么。
2. **实际缺口**：仅写可观察事实——预期与实际、对象、条件、复现性、日志/截图/计数/时间等直接证据，以及仍正常的相邻能力。不要混入原因或修法。
3. **缺口原因**：只能首先归为 `MISSING`、`EXISTING_BUT_BYPASSED`、`FALSE_POSITIVE`、`EXTERNAL_FAILURE` 或 `UNVERIFIED`。区分直接证据和推断；多种原因分行写。
4. **复用的成熟解决方案**：优先恢复原正式入口、启用已有配置/流程、复用已有测试/等待/恢复/防重机制，其次才采用同体系成熟做法或标注为推断的相似做法。仅确认 `MISSING` 后，才最小新增。

不可先想到修法再倒推前三列。无法映射到某一行的改动不进入本轮范围。

## 强制归因顺序

对每一行依序检查：

1. 是否走了正式入口？
2. 是否为检测或门禁误报？
3. 是否为外部服务、网页、网络或上游波动？
4. 证据是否足够？
5. 最后才判断为真正的 `MISSING`。

相似案例只可支持假设，不能被写成原方案事实。一次局部失败不能推翻已有验收能力。

## 改动与复测门禁

在修改前，必须能回答：该改动对应哪一实际缺口、原因有什么证据、为何不能直接恢复既有能力、以及它为何是最小成熟做法。答不清则继续取证。

每项改动记录复用对象、最小范围、明确不改范围、原失败对象的复测方式、通过条件和回退条件。修复后优先用原失败对象、输入、会话或素材复测；同时验证已成熟能力未退化。新对象通过不能代替原对象复测。

## 封袋

仅在原缺口消失、成熟能力无退化、范围未扩大、推断项已验证或仍明确标记、版本/证据/失败复盘/恢复规则均记录后封袋。禁止因顺手优化重新打开已完成范围。
