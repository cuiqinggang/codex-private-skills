# 第一性原理四列法 v4.0

## 一、核心参照系

整套方法只有一个最终参照系：

# 第一性原理物理时间

定义：

> 对一个已经固定的任务，从物理世界最基本、不可避免的步骤、计算、数据传输、存储、通信、等待和资源约束出发，推导这个任务理论上可能达到的最短完成时间。

记为：

`T_PHY`

它是方向。

它是北极星。

它不是成熟方案。

它不是当前最好成绩。

它不是某个软件的 benchmark。

它也不是要求当前阶段必须真正达到的数字。

所有优化始终回答一个问题：

> **怎样让当前真实完成时间继续向 `T_PHY` 靠近？**

---

# 二、固定任务下，时间是唯一尺度

首先固定：

`TASK`

一个 TASK 已经包含：

* 要完成什么；
* 什么算成功；
* 必须保留哪些能力；
* 输出必须满足什么条件；
* 哪些步骤不能删除；
* 哪些安全要求必须满足；
* 哪些稳定性要求必须满足；
* 哪些质量底线必须满足。

这些全部都是：

**任务定义本身的一部分。**

任务一旦固定：

唯一优化指标就是：

# TIME

即：

`T_END_TO_END`

目标：

`minimize(T_END_TO_END)`

如果通过删除任务要求、减少必要步骤、降低任务范围等方式获得更短时间：

不算优化。

属于：

`INVALID RESULT`

因此不是：

“时间和质量综合评分。”

也不是：

“时间、稳定性、GPU 利用率综合评分。”

而是：

> **固定任务下，只比较完成时间。**

---

# 三、四列正式定义

## 第一列：CURRENT

回答：

> **现在完成这个固定任务真实需要多久？**

记录：

`T_CURRENT`

以及必要的分段时间。

例如：

* 启动
* 加载
* 编码
* 计算
* 传输
* 保存
* 验证
* 返回结果

第一列只记录事实。

禁止使用：

* 感觉很慢；
* 应该差不多；
* 似乎正常；

代替真实时间。

---

# 第二列：EXTERNAL FRONTIER

回答：

> **现实世界目前已经有人把同类任务做到多快？**

来源可以包括：

* 官方方案；
* 成熟开源项目；
* 优秀工程实践；
* 公开 benchmark；
* 同类硬件实测；
* 已验证的成熟技能包；
* 已验证的成熟工作流。

第二列非常重要。

因为它告诉我们：

> 现实世界已经证明哪些事情可以做到。

但必须明确：

# 成熟方案不是最终参照系。

成熟方案只是：

* 现实证据；
* 经验库；
* 路径库；
* 可复制方案；
* 可借鉴方案。

如果成熟方案优秀：

可以直接复制。

如果成熟方案只有部分优秀：

只复制优秀部分。

如果根据第一性原理分析发现存在更优路径：

不必拘泥于成熟方案。

因此：

> **成熟方案服务于第三列。**

而不是：

> 第三列服务于成熟方案。

---

# 第三列：FIRST-PRINCIPLES PHYSICAL TIME

正式中文固定为：

# 第一性原理物理时间

回答：

> **如果从物理世界最底层重新分析，这个固定任务理论上最短需要多久？**

分析内容根据任务不同而变化。

例如 AI 推理可能包括：

* 必须读取多少数据；
* 最低需要多少计算；
* GPU 实际计算上限；
* 显存带宽；
* PCIe；
* RAM；
* 磁盘吞吐；
* 模型大小；
* 必要编码；
* 必要解码；
* 不可避免的软件调度。

部署任务可能包括：

* 必须下载多少字节；
* 网络最大有效吞吐；
* 解压；
* 安装；
* 必要验证。

故障修复可能包括：

* 最少需要哪些观察；
* 哪些诊断步骤不可避免；
* 哪一步可以并行；
* 哪一步必须顺序执行。

最终形成：

`T_PHY`

它可能首先只是一个：

`T_PHY_RANGE`

随着证据增加不断缩小。

第一性原理物理时间不要求第一次就计算得绝对准确。

但：

> **它必须始终是优化方向的参照系。**

---

# 第四列：ITERATIVE CONVERGENCE

回答：

> **怎样从当前状态不断逼近第一性原理物理时间？**

基本循环：

`测量`
→ `与 T_PHY 比较`
→ `参考成熟方案`
→ `寻找当前最大时间损失`
→ `设计一个局部优化`
→ `真实运行`
→ `重新计时`
→ `有效则保留`
→ `无效则回滚`
→ `继续迭代`

这一列的目标不是：

> 追上成熟方案。

而是：

> **利用成熟方案以及其他所有合理办法，继续朝 `T_PHY` 靠近。**

---

# 四、成熟方案的真正位置

成熟方案具有两个不同含义。

## A. 外部成熟方案

属于第二列：

`EXTERNAL FRONTIER`

作用：

提供现实世界已经验证的路径。

---

## B. 我们自己形成的成熟方案

每完成一个：

`99`

就形成一个新的：

`FROZEN MATURE BASELINE`

这个成熟版本将成为下一阶段的起点。

因此最终成熟方案并不是最后突然产生。

而是：

`成熟方案 1`
→ `99`
→ `成熟方案 2`
→ `99`
→ `成熟方案 3`
→ `99`
→ `成熟方案 4`
→ …

不断叠加形成。

最终极限版系统实际上是：

> **大量阶段性成熟方案连续迭代形成的结果。**

---

# 五、99 分到底是什么意思

99 分必须明确。

它不表示：

* 比外部成熟方案更快；
* 达到了第一性原理物理时间；
* 达到了 `T_PHY × 1.01`；
* GPU 达到理论峰值 99%。

99 分表示：

> **在当前实际硬件、软件、环境、任务定义和当前已知可验证方法下，经过系统搜索、分析和实际迭代以后，已经没有发现还能带来显著稳定时间收益的可行方案。**

即：

`CURRENT_STAGE = CONVERGED`

达到当前阶段：

`99`

---

# 六、99 与第一性原理物理时间的关系

假设：

`T_PHY = 10s`

外部成熟方案：

`T_EXTERNAL = 18s`

我们的初始版本：

`T_CURRENT = 60s`

我们首先可以复制成熟方案：

`60s → 20s`

然后继续优化：

`20s → 17s`
→ `15s`
→ `14s`
→ `13.8s`

最后发现：

在当前实际环境下，所有已知成熟、可复现、低风险、高价值方法已经测试。

继续修改预计只能：

`13.8s → 13.75s`

收益已经没有现实意义。

那么：

`13.8s`

可以成为：

`99`

即使：

`13.8s > T_PHY 10s`

依然可以是本阶段 99。

因为：

> 99 表示“当前能够达到的阶段极限”。

而不是：

> 99 表示“已经达到物理极限”。

---

# 七、99 仍然始终面向 T_PHY

即使当前阶段已经冻结为 99：

`T_99 = 13.8s`

而：

`T_PHY = 10s`

仍然必须保留：

`PHYSICAL_GAP = 3.8s`

这代表：

> 物理上仍可能存在尚未被发现、尚未成熟或当前不可实现的优化空间。

以后如果出现：

* 新算法；
* 新编译技术；
* 新 kernel；
* 新模型结构；
* 新缓存方式；
* 新成熟项目；

证明：

`13.8s → 12s`

能够稳定实现，

那么原来的：

`99`

可以重新打开。

形成新的：

`99`

因此：

> **99 是当前阶段成熟状态，不是永久真理。**

而：

`T_PHY`

始终是长期参照系。

---

# 八、如果成熟方案比我们更快

如果：

同任务、同硬件或真正可比条件下，

存在已经证明：

`T_EXTERNAL = 10s`

而我们：

`T_CURRENT = 15s`

那么原则上不能宣布：

`99`

因为第二列已经明确告诉我们：

> 有一个已知方法还能产生巨大收益。

只有以下情况之一成立以后，才可能再次讨论 99：

1. 已复制该方案并接近其结果；

或：

2. 已证明该方案实际上与当前任务不可比；

或：

3. 已证明当前真实物理/软件约束无法复现该方案；

或：

4. 已找到另一条不同路径并达到当前实际极限。

成熟方案因此不是最终目标。

但是：

> **任何已经公开证明有效的巨大收益，都不能被无视。**

---

# 九、阶段式 99 迭代

正确工程方式：

`Stage 0`
→ 99
→ Freeze

`Stage 1 = Stage 0 + 新能力`
→ 重新计算新的 `T_PHY`
→ 迭代
→ 99
→ Freeze

`Stage 2 = Stage 1 + 新能力`
→ 新的 `T_PHY`
→ 迭代
→ 99
→ Freeze

不断继续。

因此每一级都拥有：

* 当前时间；
* 外部成熟参照；
* 第一性原理物理时间；
* 迭代记录；
* 最终 99；
* 冻结版本；
* 复现方法；
* 证据。

---

# 十、新增能力只允许带来可解释的 ΔT

从：

`Stage N`

增加一个能力形成：

`Stage N+1`

必须记录：

`ΔT = T(N+1) - T(N)`

这个新增时间必须能够解释。

例如：

增加 H3。

前一级已经：

`P6 = 99`

如果根据：

* 第一性原理物理时间；
* H3 本身必须增加的计算；
* 外部成熟实现；

综合判断：

合理新增时间应该约：

`+1000s`

结果实际：

`+3600s`

那么不能说：

> H3 本来就慢。

必须首先判定：

`PATH_ARCHITECTURE_ERROR`

重新检查：

* 新增层路径；
* 工作流；
* offload；
* 模型加载；
* 重复执行；
* 软件参数；
* 前置技能包；
* 是否走错成熟路线。

---

# 十一、禁止时间崩塌成为新常态

前一级已经 99。

下一层出现数量级退化：

不能接受为新的 baseline。

正确逻辑：

`99`
→ `增加能力`
→ `异常时间`

应当解释为：

> **新增这一层存在问题。**

而不是：

> 重新从低分开始接受一个极慢系统。

这保证整个系统永远是在：

**一个已经成熟的台阶上继续向上。**

---

# 十二、局部修改原则

阶段达到 99 后：

整体结构冻结。

下一轮优先：

* 保留已经优秀部分；
* 找出时间差的局部来源；
* 只修改不足部分；
* 真实复测。

禁止为了一个局部问题大面积重构健康系统。

只有证据证明：

> 当前整体架构本身阻碍继续接近 `T_PHY`

才允许重新设计架构。

---

# 十三、整个方法最终可以压缩成一句话

# 固定任务下，以第一性原理物理时间为唯一终极参照，以成熟方案作为现实证据和路径参考，通过一个又一个阶段性的99分迭代，不断逼近当前物理世界允许的最短完成时间。

其中：

**第一性原理物理时间**

是方向。

**成熟方案**

是参考和工具。

**99 分**

是当前阶段已经达到的现实最优成熟状态。

**下一个 99**

是在前一个 99 上继续向第一性原理物理时间推进。
