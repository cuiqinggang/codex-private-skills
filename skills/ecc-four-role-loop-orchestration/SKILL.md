# ECC四角色十二层闭环编排

**当前正式版本：V2.0.1（第2版，2026-07-19）**

原始十二层资料包作为第一代历史基线，统称`V1.x`，不反向虚构当时不存在的具体补丁号；本次四角色、真实多智能体、返修闭环和新验收合同的完整重构从`V2.0.0`开始。

版本号按从小到大递增：修正错字、示例或验证漏洞时增加末位，如`V2.0.1`；兼容现有十二层的能力增强时增加中间位，如`V2.1.0`；改变十二层核心、角色责任或验收语义时增加首位，如`V3.0.0`。版本号用于直观识别先后，Git提交编号用于精确定位网上仓库中的具体内容；两者必须同时保留。

## 一、核心定位

本技能只有一个运行主轴：Claude Code风格固定十二层。四阶段、四角色、技能调用、时间规则、检查点和返修都必须落入这十二层，不能另建平行主流程。

正式长任务同时要求：真实多智能体、工程执行与独立审计分离、必需技能真实使用、现实或脚本验证、有界返修、可恢复交接和中文最终验收。

本技能领域中立。医学、工程、人工智能或其他专业能力，都在第3层按当前任务选择外部技能；任何行业都不在本技能内获得特殊流程。

## 二、启动时只读什么

1. 先读本文件。
2. 再读 `references/twelve-layer-standard.md` 的总则和当前即将运行的层；不得在启动时把全部专题资料灌入上下文。
3. 到第5层启动智能体时读 `references/four-role-parallel-runtime.md`。
4. 第3层确有外部技能时读 `references/skill-use-gates.md`；需要任务类型适配时读 `references/domain-adapters.md`。
5. 第8、9层发现失败并进入返修时读 `references/stage-repair-loop.md`。
6. 出现异常早完、跨会话恢复或耐力验证时读 `references/time-checkpoint-policy.md`。
7. 创建证据前，标准模式读 `references/standard-run-contract.md`；严格模式读 `references/run-evidence-contract.md` 和需要填写的模板小节。

历史错误矩阵、来源取舍、视频映射、官方实践核对和成熟组件资料只用于版本治理或对应问题，不参与日常默认加载。

## 三、四阶段外壳

四阶段只是责任交接，不增加层级：

1. 资料准备：确定目标、读取事实、选择技能，对应第1至3层。
2. 计划成型：拆工作包并启动真实角色，对应第4、5层。
3. 工程执行：执行、触发检查、确定性检查、独立审计和返修，对应第6至10层。
4. 强审核与交付：全局复核、压缩交接和最终验收，对应第9、11、12层。

如果没有发生真实环境交接，不为四阶段额外制造四套文档。

## 四、四类真实角色

正式长任务默认建立四个真实独立上下文：

1. 控制角色：锁定目标、拆包、调度、接收回执、冻结依赖和路由返修。
2. 资料角色：只读核实来源、准备项目记忆、技能和小型资料包。
3. 工程执行角色：在受控可写空间生成第一版和修复版，只提交执行声明。
4. 独立审计角色：默认只读，从验收标准重新检查并独立接受或拒绝。

固定的是四类责任，不是智能体总数。复杂任务可按独立工作包增加多个资料、工程执行或审计智能体；新增实例必须有独立上下文、空间、边界、回执和可测收益。禁止复制同一任务凑数量。

只有控制角色维护完整十二层状态。子智能体默认只接收当前角色边界、当前工作包、相关层要求、验收标准、必需证据和输出格式；只有工作包明确触发专题规则时才按需读取对应资料，禁止每个子智能体重复加载整个ECC包。

“逻辑隔离”只帮助整理资料，永远不能代替真实子智能体。系统暂时无法启动真实子智能体时，只能完成准备工作并标记阻塞，不能走单智能体正式通过路线。

允许的机器角色只有 `control`（控制）、`materials`（资料）、`execution`（工程执行）、`audit`（独立审计）。文章、说明和交接文件如属于工程任务，由工程执行角色生成，不另设写作者角色。

## 五、固定十二层

名称、中文解释、顺序和权责固定如下：

1. `Control Plane / Orchestrator`（主控调度层）
2. `Short Entry / Memory`（短入口 / 项目记忆层）
3. `Skills / Progressive Disclosure`（技能按需加载 / 渐进加载层）
4. `Planning / Work Decomposition`（任务拆解层）
5. `Subagents / Context Isolation`（子智能体 / 上下文隔离层）
6. `Execution Plane`（执行平面）
7. `Hooks / Lifecycle Triggers`（生命周期钩子层）
8. `Scripts / Deterministic Checks`（脚本确定性检查层）
9. `Verification Plane`（独立验证平面）
10. `Repair Loop`（返修循环层）
11. `Compact / Handoff`（压缩交接层）
12. `Final Acceptance`（最终验收层）

`references/twelve-layer-standard.md` 是完整中文权威正文。每层的定位、目的、输入、动作、产物、文件要求、内容要求、禁止事项、时间关联、多智能体要求、验证方法、失败返回、证据路径、下一层条件、本任务应用和不可跳过规则，均不得删改。

一项正式任务只有一套任务级十二层。工作包在第4层登记，只在第6至10层分别经历执行、检查、审计和返修；不得为每个工作包复制整套十二层。

标准证据模式通过“标准版本及校验值”继承每层固定十六项，只记录本次输入、实际动作、新增产物、证据、状态和下一关口。严格审计模式才逐层展开十六项运行实例。这是把固定规范与运行事实分开，不是把十二层压缩成摘要。

## 六、技能使用硬门

1. 第3层确认技能入口、版本、依赖、适用范围和必读资料。
2. 第4层把必需技能绑定到工作包；第5层绑定到真实智能体。
3. 第6层开始前检查实际读取或调用证据。
4. 第8层检查技能要求的命令、产物或工具回执；第9层独立接受。
5. 未准备、未分配、未实际使用或无法举证时，当前工作包立即阻断并返回第3、5或6层；不得等到第12层才发现。

不需要外部技能时明确写“无必需外部技能及理由”，不得为满足形式虚构技能。

## 七、闭环放置位置

每个工作包运行同一闭环：

```text
第6层产生第0轮第一版
→ 第8层运行成功、错误和安全检查
→ 第9层独立接受或拒绝
→ 被拒绝项进入第10层定位根因和改变策略
→ 返回第6层修复
→ 重新经过第8层和第9层
→ 通过、部分完成、阻塞或拒绝
```

默认最多三轮返修。第一轮返修起必须改变假设、策略、拆包或目标层；重复同一失败和同一修复不计为新一轮。达到上限仍有关键失败时停止该工作包，不受影响的独立工作包可继续。

## 八、时间规则

- 普通生产任务：设置预计时间范围或最长预算，不设必须耗满的最低时长。完成全部目标、检查和独立审计后立即结束。
- 每个生产和开放式优化任务都由独立审计角色做早完异常判断。明显早于可靠历史范围时进入专项复核；没有可靠历史数据时，首次运行直接做完整保守复核。通过就接受效率收益，失败就返修，禁止等待补时间，也禁止使用写死比例判失败。
- 开放式优化任务：第4层先定义基线、目标、候选方向、无收益轮数、成本或风险上限、最长窗口和独立停止审计者；仍有可测收益才继续，满足预设停止合同并通过独立审计时可提前结束。
- 耐力验证任务：只有“持续运行能力”本身是目标时，最低真实时长才是验收条件；每个检查点必须有新增工作或证据，禁止睡眠、空等和重复输出。

时间只是资源和异常信号，不能替代结果关口。详细规则见 `references/time-checkpoint-policy.md`。

## 九、证据分级

默认使用标准模式，避免证明材料吞噬任务本体：

- 标准模式：一般可逆工程长任务，使用7个合并证据文件和 `scripts/validate_standard_evidence.py`。
- 严格模式：用户要求完整法证审计、不可逆部署、高风险外部发布、多系统迁移、修改ECC本身、批量改变全局技能或自动触发规则、证据争议或历史造假复现时，使用现有20文件合同和 `scripts/validate_run_evidence.py`。普通单技能可逆修改仍使用标准模式。
- 耐力验证：使用严格模式，并增加真实时长、恢复和连续进展证据。

验证脚本只检查可确定事实，不能替代第9层独立审计和第12层最终验收。真实智能体必须有系统侧启动和回传记录；角色文件中的自述不算回执。

## 十、最终关口

- 第6层只能声明做了什么。
- 第8层脚本通过不等于任务通过。
- 第9层必须由不同智能体独立验收。
- 第10层必须关闭或明确隔离所有拒绝项。
- 第11层只交接和恢复，不冒充最终验收。
- 第12层只能汇总前面已通过的目标、技能、多智能体、检查、审计、返修和安全关口。

最终状态只有：通过、部分完成、阻塞、拒绝。面向用户以中文报告；必要英文标识后立即写中文解释。

## 十一、环境边界

在用户既有环境中，C盘是正式权威源；H盘只作历史记录；K盘只有用户明确同意时才作备份。不得伪造缺失历史、覆盖旧ECC或把候选目录说成正式部署。
