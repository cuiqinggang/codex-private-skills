# 严格审计模式结构化运行证据合同

本合同只在用户要求完整法证审计、不可逆部署、高风险外部发布、多系统迁移、修改ECC本身、批量改变全局技能或自动触发规则、证据争议、历史造假复现或耐力验证时启用。普通单技能可逆修改和一般工程任务默认使用`standard-run-contract.md`的七文件合同。

## 一、为什么不能再简化成几个布尔值

“十二层完整=true”“真实多智能体=true”只是自述，不能证明十二层真的运行、智能体真的启动、技能真的使用。正式证据目录必须同时覆盖原目标、逐层实例、角色、声明、产物、检查、审计、返修、交接和最终验收。

机器字段保留英文以便脚本读取；用户报告、结论、理由和错误必须提供中文。

## 二、必需文件

| 文件 | 中文作用 |
|---|---|
| `run-config.json` | 任务、项目、权限、多智能体、时间、成熟组件和模型工具路线 |
| `layer-status.json` | 十二层逐层十六项中文运行实例 |
| `declared-requirements.json` | 用户已声明要求 |
| `completion-ledger.json` | 每项要求的完成台账 |
| `source-confidence-register.json` | 来源、断言、置信度和下游限制 |
| `tool-inventory.json` | 工具、认证、上下文成本和密钥风险 |
| `agents.json` | 真实智能体启动、回传、空间、责任和贡献 |
| `work-packages.json` | 工作包、技能、执行者、审计者和验收合同 |
| `execution-claims.json` | 第6层逐条执行声明 |
| `artifact-manifest.json` | 产物路径、校验值、生产者和处置 |
| `deterministic-checks.json` | 正常、错误、结构和安全检查 |
| `claim-acceptance-matrix.json` | 第9层逐声明接受或拒绝 |
| `rounds.json` | 第0轮第一版和第1至3轮返修 |
| `checkpoints.json` | 真实时间、动作、产物和审计检查点 |
| `delivery-safety-check.json` | 元数据、密钥、内部路径、临时材料、附件和引用复检 |
| `handoff.json` | 压缩交接、会话快照、恢复入口和剩余风险 |
| `evidence-index.json` | 所有证据编号、路径、校验值和旧产物名映射 |
| `final-acceptance.json` | 机器可读最终验收 |

| `final-report.md` | 中文最终报告 |

双份最终验收缺一不可。文件名需要改变时，必须在证据索引和交接包中建立别名，不得静默接受。

## 三、十二层实例

`layer-status.json`必须恰好十二项，英文名、固定中文名和顺序与主标准一致。每项至少包含：

```json
{
  "layer_number": 1,
  "english_name": "Control Plane / Orchestrator",
  "chinese_name": "主控调度层",
  "status": "PASS",
  "skippable": false,
  "positioning": "本层定位",
  "purpose": "本层目的",
  "inputs": ["本层输入"],
  "actions": ["本层动作"],
  "artifacts": ["本层产物"],
  "file_requirements": ["本层文件要求"],
  "content_requirements": ["本层内容要求"],
  "prohibitions": ["本层禁止事项"],
  "time_policy": "本层时间关联",
  "multi_agent_requirements": "本层多智能体要求",
  "verification_method": ["本层验证方法"],
  "failure_return": "失败返回",
  "evidence_paths": ["证据路径"],
  "next_layer_condition": "下一层条件",
  "task_application": "本任务中的具体应用"
}
```

不能用一个`twelve_layers_complete`布尔值代替本文件。

## 四、已声明要求和完成台账

每项用户强制要求进入`declared-requirements.json`，包含编号、中文说明、关键性和验收标准。`completion-ledger.json`对每项要求记录接受、用户豁免、阻塞或拒绝，以及证据编号和中文结论。

最终通过只允许全部已声明要求为接受；豁免必须来自用户，不能由模型自己放弃要求。

## 五、角色和工作包

每个真实智能体至少记录：唯一编号、父级、四类角色之一、独立上下文、独立工作空间、系统启动与回传回执、不可由智能体自填的回执来源、回执原始证据编号、平台运行编号、父级平台运行编号、真实起止时间、有边界责任、实际工作证据、可测收益和合并成本。角色文件里自写“已启动”不属于系统回执。回执事件文件必须与`agents.json`中的智能体、上下文、父子关系、起止事件和时间逐项一致。

工作包的执行者必须是执行角色，审计者必须是不同的审计角色。每包至少有要求编号、必需技能和实际使用证据、验收标准、确定性检查、回滚、停止条件和第0轮第一版。技能使用证据必须进入证据索引，并指向运行工具导出的读取／调用事件；工作包内自行填写“已经使用”不能单独过关。每项已声明要求还必须进入工作包和执行声明，不能只在最终完成台账中被口头接受。

准备任务在系统没有真实子智能体时可以保存准备成果，但必须明确最终状态为阻塞或部分完成，并保存不可用原因；这种结构检查通过不等于正式生产任务通过。

## 六、执行、检查、审计和返修

- 每条执行声明引用工作包、执行者和产物编号；
- 每个产物有正式／影子路径、证据目录内副本、真实校验值、生产者、类型和处置状态；
- 每个检查有命令或方法、预期、观察、结果和证据编号；
- 正式通过时每个工作包至少有一个成功信号和一个错误案例；
- 每条声明都进入独立验收矩阵，并完成事实复核和交付复检；
- 轮次必须从0开始连续；任何失败后的下一轮都必须改变策略；
- 执行者和审计者必须与工作包绑定一致。

## 七、检查点和耐力恢复

每个检查点必须记录真实时间、层、工作包、真实进展、证据编号，并至少包含产物差异、命令／测试或审计决定之一。

生产任务按事件和里程碑记录，不制造空心跳。耐力任务还必须证明原始开始时间未重置、结束时间有效、持续运行驱动、最终检查点、中断与恢复事件、晚检查点原因和真实时间对应；“仅已部分启动”不是有效停止状态。

## 八、早完异常判断和专项复核

每个生产和开放式优化任务都由独立审计角色记录：是否有可靠历史范围、历史依据、预计下界、本次是否异常、目标数、工作包数、产物数、检查数和中文判断理由。禁止使用“时间预算×固定比例”决定是否复核。

实际用时低于可靠历史下界时必须专项复核；没有可靠历史数据时，首次运行也必须专项复核。复核逐项确认目标、工作包、技能、多智能体回执、真实产物、确定性检查、错误案例、跳过项和审计独立性。

复核通过立即接受效率收益，不等待补时间；复核失败进入返修。

## 九、证据别名

`evidence-index.json`的`aliases`必须映射：执行声明、产物清单、脚本验证结果、声明验收矩阵、返修记录、压缩交接、证据索引、双份最终验收和最终报告。这样即使文件改名，也不会丢失原ECC硬门。

证据索引中的路径必须是证据目录内的相对路径，文件必须真实存在，校验值必须与当前内容一致。验证器拒绝绝对路径、越出证据目录的路径和虚假校验值。

真实智能体回执还必须保存运行平台导出的原始事件文件，并在`agents.json`中引用对应证据编号。验证器能够确认事件文件存在、路径没有越界且内容校验值一致，但不能单独证明该文件一定由平台签发。第9层审计必须再把事件编号、时间和父子关系与平台界面、运行接口或受信事件日志逐项对照；没有平台侧可核对来源时，只能记录为“证据不足”，不能正式通过。

## 十、运行验证器

```bash
python3 scripts/validate_run_evidence.py <证据目录>
```

验证器通过只代表结构和可确定关口成立。第9层独立审计、第12层最终验收和必要的人工关口仍不可替代。
