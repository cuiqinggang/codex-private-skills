# 《当前任务目标与正反约束｜任务合同规范 第2版》

规范版本：第2版
状态：CURRENT
当前活动任务：NONE

## 1. 任务合同只回答“要什么”

任务合同是任务级唯一权威。

它只锁定：
- 用户最终现实目标；
- 正向必须项；
- 反向禁止项；
- 完成标准；
- 证据标准；
- 用户现实操作路径；
- 范围和硬边界。

它不负责“现在做到哪里”，也不规定冻结版本如何递增；这些属于执行大脑与当前任务冻结状态。

## 2. 初次接到现实任务的固定生成流程

### 第1步：保留用户原始意图
记录用户原始任务的最小忠实摘要。
不得先把用户任务改写成某个实现方案。

### 第2步：提炼最终现实目标
只写“用户最后真正要得到什么”。
实现工具、模型、代码结构、网页步骤默认不属于目标，除非用户明确把它们作为结果要求。

### 第3步：生成正向约束
只列：
- 必须具备；
- 必须保留；
- 不能为了更快而牺牲；
- 用户真正关心的质量、功能、体验。

### 第4步：生成反向约束
只列：
- 绝不能发生；
- 表面完成但现实不接受；
- 属于目标漂移；
- 降质、绕路、假完成、错误替代；
- 用户明确禁止的操作。

### 第5步：冻结范围与硬边界
明确：
- 必须完成；
- 明确不做；
- 不可突破的边界。

### 第6步：冻结用户路径
写出用户最终最简现实操作路径。
用户路径不合格的方案不得成为正式冠军。

### 第7步：定义最终验收标准
把目标改写成明确、可观察、可判断的完成条件。
禁止用“看起来差不多”“应该可以”代替最终有效标准。

### 第8步：定义必要证据
证据只服务于证明完成条件，不为堆日志。

### 第9步：反向漏洞检查
逐项检查：
- 是否可能满足文字却没有满足用户真实目标；
- 是否可能更快但质量或功能变差；
- 是否可能测试通过但真实任务失败；
- 是否依靠额外人工才能成立；
- 是否违反硬边界。

有漏洞先修合同，不进入执行。

### 第10步：冻结任务合同
首次正式冻结：
CONTRACT_VERSION=1

后续如何建立《当前任务冻结状态 第1版》及如何递增，由《极限短时间执行大脑》负责，不在本合同规范重复定义。

## 3. 标准任务合同

```yaml
TASK_ID: <唯一任务编号>
CONTRACT_VERSION: 1

USER_REQUEST_RAW: >
  <用户原始意图的最小忠实摘要>

FINAL_REALITY_GOAL: >
  <最终现实结果，不先写实现>

POSITIVE_PROMPT:
  - <必须实现/保留>

NEGATIVE_PROMPT:
  - <禁止/失败/漂移项>

IN_SCOPE:
  - <必须完成>

OUT_OF_SCOPE:
  - <明确不做>

HARD_BOUNDARIES:
  - <不可突破>

USER_PATH:
  - <用户最简操作>

FINAL_VALID_STANDARD:
  - <最终有效标准>

DONE_WHEN:
  - <可验收完成条件>

EVIDENCE_REQUIRED:
  - <必要证据>
```

## 4. 后续执行不得重写合同

以下情况不改变任务合同版本：
- 换 CEO 页面；
- 换 Executor；
- 节点成功或失败；
- Reality Delta；
- 修复问题；
- 更换更快成熟路线；
- T* 更新；
- 新增证据。

## 5. 任务合同版本升级

只有以下实质变化才允许：

1 → 2 → 3 → ...

- 用户最终目标改变；
- 最终验收标准被 Reality 证明定义错误或不足；
- 正向约束改变；
- 反向约束改变；
- 范围或硬边界改变；
- 用户路径本身变成新的硬要求。

升级必须明确写出：
旧版本
→ 改变原因
→ 改变内容
→ 新版本

旧版本保留，不静默覆盖。

## 6. FINAL_VALID 门

FINAL_VALID=YES 只允许同时满足：

完成条件全部满足
+
必要证据足够
+
反向约束未触发
+
硬边界未违反
+
用户路径合格（用户型任务）

否则只能 NO 或 UNKNOWN。

## 7. 与冻结状态的分工

任务合同：
**应该做什么，什么叫完成。**

《当前任务冻结状态 第N版》：
**现在做到哪里，下一步从哪里恢复。**

两者不能互相替代。

一句话：

**初次接任务先把用户真实目标变成可验收、可防漂移的任务合同；后续执行只推进状态，不偷偷改题。**
