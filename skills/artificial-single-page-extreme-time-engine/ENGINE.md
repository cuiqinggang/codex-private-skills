# 《人工单页面极限短时间引擎 第7版》

版本：第7版  
状态：CURRENT  
唯一标准：`T*=min(T_VALID)`

## 1. 本版修正的核心错误

第6版在 Greenfield R1-R10 中被错误解释为：

```text
每页一个自然逻辑节点
≈ 每页只能改一个微变量
≈ 每改一个点就必须做一次正式 Reality
≈ 每次 Reality 后必须冻结并换页
```

该解释废止。

正确语义：

```text
页面 = 一个明确任务/分支的连续工作容器
自然逻辑节点 = 一个可闭合的目标
微变量 ≠ 自然逻辑节点
```

同一页面内，GPT 可以围绕同一个闭环目标连续进行多轮虚拟攻击、组合多个彼此兼容的优化、并行分析多个独立瓶颈，直到形成一份成熟冻结方案；然后再做 Reality。

## 2. 正确闭环

```text
任务接受
→ 冻结 VALID / READY_STATE / 边界
→ 成熟方案集群检索
→ 虚拟成熟循环
   ├─ 找最大瓶颈
   ├─ 删除伪依赖
   ├─ 并行独立判断
   ├─ 组合兼容优化
   ├─ 估算预期节省
   └─ 继续循环直到收益收敛
→ Freeze 一份“整包成熟方案”
→ 一次正式 Reality
→ VALID 验收
→ 若失败：按现实差异回虚拟层重新成熟
→ 若成功：记录 T_VALID / T*
```

Reality 是“冻结方案验证器”，不是“逐点优化器”。

## 3. 单变量规则的正确适用范围

“单变量 Reality”不是默认工作法，只在以下情况使用：

1. 必须隔离因果，且多个变化会让结果不可判定；
2. 高风险变化可能改变 VALID；
3. 两个候选路线差异很小，需要 A/B 现实证据；
4. 某个 Failure Class 的根因仍不确定。

以下情况禁止强制单变量：

- 已经有明确依赖图；
- 多个优化彼此独立或兼容；
- 只是常规性能收敛；
- 成熟方案已经能一次覆盖多个已知缺陷；
- 纯粹为了“每页一个点”而拆分。

## 4. “局部最小修复”边界

局部最小修复只适用于“已证实的局部 bug / Failure Class”。

不得把它扩展为：

```text
整个项目永远只允许一次改一个点
```

Greenfield、性能成熟、结构优化允许在虚拟层一次组合多个兼容改进。

## 5. 页面边界

页面隔离继续保留，但解释为：

- 一个页面只服务一个明确任务/分支；
- 不在同一页混跑两个无关项目；
- 页面内部允许多轮虚拟成熟；
- 页面内部允许并行独立分析；
- 页面内部允许形成一个“成熟改进包”；
- 不要求每个微优化单独换页；
- 只有任务切换、分支切换、上下文接近失效、Reality 冻结交接或恢复需要时才换页。

## 6. Reality 数量最小化

默认目标：

```text
先在虚拟层尽量成熟
→ 尽量用 1 次 Reality 证明整个冻结包
```

正式 Reality 不是免费的探针。若可通过代码分析、成熟方案、依赖关系、已有证据消除不确定性，不得浪费一次 Reality。

## 7. 性能剖面

性能打点应在第一次正式成功前尽量一次布好，避免为了“新增观测字段”单独消耗一轮正式 Reality。

基础阶段统一使用：

- 输入/解析
- 启动/连接
- 等待
- 发现/扫描
- 分类/判断
- 下载/执行
- 合并/提交
- verifier
- 未分类胶水时间

测试器只观察，不改变业务语义。

## 8. 组合优化规则

先建立依赖图，再决定是否可组合：

```text
独立 → 并行或同包修改
依赖 → 按依赖顺序
互斥 → 候选分支比较
因果不清 → 单变量 A/B
```

禁止把“独立可组合”强制拆成串行版本。

## 9. 抖音 Greenfield R1-R10 反例

本轮真实证据证明，第6版被错误执行成了串行器：

- R1：候选选择未做真实轨道分类；
- R2：失败证据未完整持久化；
- R3：首次已经 PASS，却误启动第二次 Reality，并删除有效成品；
- R4：才补齐 exactly-once、staging、原子提交；
- R5：只攻击固定 wait；
- R6：单独用一轮 Reality 只做性能打点；
- R7：只删 300ms 稳定等待；
- R8：只改 goto 到 commit，失败；
- R9：只把 fallback 4.5s 改 7s；
- R10：只把 threshold 3 改 2，反而慢一倍。

这些变化中，大量内容本可在虚拟成熟阶段一次组合成一个更成熟候选，而不需要逐页逐点 Reality。

## 10. 停止条件

当以下条件成立即可停止主动优化：

- FINAL_VALID=YES；
- 主要结构性浪费已消除；
- 下一候选收益低于现实抖动或维护复杂度；
- 没有高置信度、低风险、大收益优化待验证。

允许保留历史最短有效观测为 `T*`，但不得因为 0.x% 的单次抖动差异无限制造新版本。

---

本版优先级：  
**成熟整包 > 单点串行；虚拟循环 > Reality 循环；依赖图 > 固定流程。**


## 11. 时间层级不可混淆

同一个公式可以用于不同任务，但任务边界必须先冻结。

若当前任务是“做出成熟下载器”，则该任务的正式时间必须覆盖：

```text
原始任务接受
→ 虚拟成熟
→ 实现
→ Reality
→ 修复/重冻结
→ 第一个成熟 FINAL_VALID
```

单次“复制链接→双击→MP4”的 15 秒左右，只是**生产运行子任务**的 T_VALID，不能替代“把下载器做成熟”这一上层任务的端到端 T_VALID。

因此以后同时记录但不得混称：
- 上层建设任务：从 TASK_ACCEPTED 到成熟 FINAL_VALID；
- 下层生产任务：从合法 READY_STATE 到单次下载 FINAL_VALID。

唯一目标仍是各自任务定义内的 `T*=min(T_VALID)`，不是增加第二评分目标。


## 12. 新方法 Reality 轮数上限

用于验证“方法是否真的更快”的新任务，不允许再次无限派生版本。

默认：

```text
TARGET_REALITY_ROUNDS = 3..4
HARD_MAX_REALITY_ROUNDS = 5
```

规则：

1. 首轮前必须完成整包虚拟成熟，不得把第1轮 Reality 当探索起点。
2. 若第1–3轮已经稳定达到 FINAL_VALID，且没有高置信、大收益、低风险结构改进，允许提前 STOP。
3. 若第3–4轮仍有明确结构性收益，可继续，但总 Reality 不得超过5轮。
4. 到第5轮仍未收敛、仍依赖微调、或只剩现实抖动：
   `MANDATORY_POSTMORTEM=YES`，立即停止继续派生版本。
5. 复盘后若方法本身有缺陷，先升级方法，再另立新验证任务；不得在原任务上无限 R6/R7/R8…。
6. 轮数上限约束的是方法验证成本，不降低 VALID 标准。
