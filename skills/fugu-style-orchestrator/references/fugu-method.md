# Fugu 式方法拆解

## 1. 准确定义

Fugu 式方法不是“训练一个单体全能模型”，而是把多个模型、工具、验证器和任务流程包装成一个统一入口。外部像调用一个模型，内部像一个会动态调度的小型智能团队。

核心公式：

```text
用户任务 -> 任务识别 -> 路由决策 -> 专家模型/工具执行 -> 验证/修复 -> 单一最终答案
```

Sakana Fugu 的特别之处在于：调度器本身也是训练出来的语言模型或决策模块，而不只是人工写死的 if/else 路由。

## 2. 关键概念

| 概念 | 含义 | 可复刻程度 |
|---|---|---|
| Orchestrator | 总调度器，判断任务该由谁做 | 可用 GLM/Kimi/规则路由复刻 |
| Worker pool | 底层专家模型池 | 可用 DeepSeek/Kimi/Qwen/GLM/OpenRouter 模型池复刻 |
| Agentic scaffold | 针对当前任务临时生成的工作架构 | 可用技能包和命令包复刻 |
| Verifier | 独立检查输出是否正确 | 可用 GLM 或第二模型复刻 |
| Repair loop | 验证失败后定向修复 | 可用 Codex/Kilo 长任务循环复刻 |
| Synthesis | 把多个输出合成一个答案 | 可用最终控制层复刻 |

## 3. 标准工作步骤

1. **入口统一**
   - 用户只提交一个任务。
   - 系统内部决定是否需要知识库、联网、代码执行、视觉识别、多模型审查。

2. **任务识别**
   - 判断任务类型：代码、数学、研究、图像、UI、自动化、法律/医学/金融、长上下文、普通写作。
   - 判断复杂度：简单、复杂、高风险、长流程。
   - 判断约束：成本、时长、是否允许外部模型、是否需要隐私隔离。

3. **路由选择**
   - 简单任务：单模型直接答。
   - 中等任务：主模型执行 + 验证模型检查。
   - 高难任务：规划、执行、专家、验证、修复、合成分离。
   - 极高难任务：加入 Fugu Ultra 或其他高端模型做最终裁判或对照。

4. **角色分配**
   - Planner：拆解任务。
   - Executor：执行主体。
   - Specialist：处理特定难点，如视觉、代码、长文、搜索。
   - Verifier：找错、查证、验收。
   - Repairer：根据失败项修复。
   - Synthesizer：最终合成。

5. **执行与记录**
   - 每个角色只拿到必要上下文，避免上下文污染。
   - 每步产出结构化记录：输入、模型、动作、证据、失败点。
   - 长任务必须有 checkpoint 和 heartbeat。

6. **验证与修复**
   - 验证器按固定 rubric 检查。
   - 不通过时只把失败证据发给修复角色，避免重复整个上下文。
   - 修复后必须再验收一次。

7. **最终交付**
   - 合成单一答案或交付物。
   - 标明事实依据、未验证部分、成本、模型分工。
   - Codex 任务按用户规则打包三位数字 ZIP。

## 4. Fugu 的优势到底在哪里

### 4.1 它承认模型各有专长

单模型路线假设“一个模型什么都会”。Fugu 式路线假设：

```text
没有一个模型永远最强，但某个任务一定有更适合的模型组合。
```

这和用户现有思路一致：DeepSeek 写代码、GLM 做控制/Gate、Qwen 做视觉、Kimi 做长上下文/Agent 编程、便宜模型做批处理。

### 4.2 它把“脚手架能力”当成能力本身

在代码任务里，模型的原始智力只是一部分。真正决定成败的是：

- 是否会读仓库。
- 是否会运行测试。
- 是否会根据错误修复。
- 是否会保留用户改动。
- 是否会做最终验收。

Fugu 式方法把这些脚手架变成核心能力，而不是附属功能。

### 4.3 它用验证抵消单模型盲点

多模型系统不是为了“热闹”，而是为了制造不同角度：

- 执行模型负责完成。
- 验证模型负责不相信它。
- 修复模型负责针对证据修。
- 合成模型负责把结果压成用户能用的交付。

### 4.4 它适合长流程和高难任务

最适合的任务：

- 复杂代码修复。
- 代码审查。
- 论文复现。
- 多资料研究。
- 安全分析。
- 自动化流程设计。
- 多模态证据检查。
- 需要多轮失败修复的任务。

不适合的任务：

- 简单问答。
- 低价值闲聊。
- 大量廉价批处理。
- 用户只要快速草稿。

## 5. Fugu / Fugu Ultra 的差别

| 模式 | 目标 | 典型行为 | 适合场景 |
|---|---|---|---|
| Fugu | 平衡性能和延迟 | 多数情况下选择一个最适合 worker | 日常编码、互动问答 |
| Fugu Ultra | 质量优先 | 更深专家池、多 agent、多轮验证 | 高难研究、代码审查、论文复现 |

复刻时也要分两档：

- **低成本 Fugu 模式**：只做智能路由，尽量一个主模型解决。
- **Ultra 模式**：只有任务价值足够高时，才启动多模型并行、验证和修复。

## 6. 局限与风险

1. **宣传可能放大**
   - “接近 Fable 5 / Mythos Preview”不能自动等于“全面超过 Mythos 5”。
   - 多数公开报道转述官方分数，独立复测仍有限。

2. **底层模型不透明**
   - 真 Fugu Ultra 的 worker pool 固定，不完全知道每次用了谁。
   - 自建复刻版要记录每个角色使用的模型，保持可审计。

3. **成本可能失控**
   - 多 agent 会增加输出和中间步骤。
   - 必须先设预算、轮数、最长上下文、失败停止条件。

4. **延迟明显增加**
   - 越像 Ultra，越慢。
   - 需要为长任务设计 checkpoint，而不是等一个黑盒回答。

5. **验证器也会错**
   - 验证器不能只看语言流畅度。
   - 对代码必须运行测试；对事实必须查源；对视觉必须看图；对文件必须读回。

## 7. 本技能包复刻的目标

本技能包不是复制 Sakana 的私有训练权重，而是复制它的方法论：

```text
统一入口
动态路由
专家分工
证据驱动
验证修复
成本控制
可复现实验
```

如果以后要升级成真实系统，优先实现：

1. 任务分类器。
2. 模型能力矩阵。
3. 成本估算器。
4. 角色化 prompt 模板。
5. 验证 rubric。
6. 失败修复循环。
7. 基准测试记录。
