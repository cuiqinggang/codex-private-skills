# 可持续正常态故事法｜v1.0

版本：1.0
状态：FROZEN
定位：把强现实需求写成“故事”，先构造可长期成立的正常态，再用风险/故障案例攻击并逐版本修正。

## 1. 核心目标

不以“研究所有失败”为主线，而以“什么状态可以长期正常运行”为主线。

固定主线：

```text
现实故事
→ 明确人物/环境/能力/约束
→ 定义 NORMAL_STATE（正常态）
→ 提取长期成功样本的共同不变量
→ 构造 NORMAL_ZONE（正常区间）
→ 用故障/风险/变化案例攻击
→ 找到会把系统推出正常区间的条件
→ 增加必要保护、冗余或约束
→ Reality 验证
→ 形成下一版本故事
```

## 2. 第一性原理

1. 公共产品/服务必须存在可持续的正常使用区间，否则其正常商业与使用逻辑无法成立。
2. 正常态不是一个静止点，而是允许现实波动的一段区间。
3. 目标不是贴近未知阈值运行，而是长期保持在正常区间内部并留有余量。
4. 失败案例只用于攻击、验证和修正正常态，不作为整个任务的唯一主线。
5. 成熟方案、公开经验、同类案例和工具都可以复用，但它们只用于加速正常态构造与验证。
6. 对第三方服务只采用合法、官方允许、可持续的正常使用条件；不以规避平台安全、风控、身份或访问限制为目标。

## 3. 故事模板

每个版本只回答以下问题：

- **人物**：谁在使用？
- **目标**：要长期得到什么现实结果？
- **环境**：设备、地区、网络、账号、支付、客户端、工作方式等现实条件是什么？
- **已有能力**：当前能控制什么、不能控制什么？
- **正常态**：什么状态下任务可以长期正常完成？
- **允许波动**：哪些变化仍属于正常区间？
- **攻击案例**：哪些现实变化可能破坏正常态？
- **保护条件**：怎样让这些变化不轻易把系统推出正常区间？
- **Reality**：怎样验证这个故事在现实中成立？
- **下一版本**：新的现实证据改变了什么？

## 4. 版本规则

- v1.0：建立故事、目标、正常态和攻击法。
- 后续版本：只在出现新的现实证据、成功模式、失败模式或边界时升级。
- 每次升级都保留前一版本已经验证成立的部分，不重新从零设计。
- 版本升级优先“少改、可验证、可回滚”。

## 5. 与故障修复方法的关系

正常态故事法负责：

```text
怎样长期不坏
```

故障差分修复负责：

```text
真坏了以后怎样最快恢复
```

两者统一于第一性原理：

```text
正常态构造
→ 风险攻击
→ 若仍正常：继续
→ 若失效：LAST_GOOD → 重现 BAD → 缩小边界 → 最小 Repair
→ 回到 NORMAL_STATE
```

## 6. v1.0 冻结结论

一句话：

> 先把现实需求写成一个能够长期成立的正常故事；再让各种风险去攻击这个故事，能承受就保留，不能承受就最小修正，逐版本把故事推向稳定、可验证、可长期维持的正常态。
