## 一、反复出现过的症结与最小纠正

| 编号 | 已见异常／容易误判的现象 | 可确认的症结与成熟做法 | 修复完成条件 |
|---|---|---|---|
| 01 | 原统一监控十行挤在一起，需最大化才能看全 | 原 PowerShell 表格布局拥挤，用户日常只需异常；切换精简中文窗口，保留完整版备份 | 不最大化可读、十方向仍在快照、只显示必要摘要与故障 |
| 02 | 全功能监控过重，可能抢占执行资源 | Grafana 曾有约501.5MB、停止前351.5MB工作集；把高级软件／工具与日常目录分离，**停止服务和开机启动**，而非删除历史 | `grafana.exe` 为0、轻量窗口运行、后台采集未停、归档SHA一致 |
| 03 | 重建监控底座／自制大型界面 | 优先使用原生 Task Scheduler＋PowerShell 7／现有JSON事件，复杂监控需时复用Grafana OSS＋官方Infinity插件 | 不开发新的数据库／调度器／Agent框架，原业务运行器未改变 |
| 04 | 监控显示英文状态码／播报英文 | 状态码用于内部判定，显示和语音走中文映射；不向用户输出 `API_INVOKED`／`ENGINE_EXIT_0` 等技术码 | 正常页面、异常页面、文字提醒及内建中文语音调用实际检查 |
| 05 | 监控每分钟刷新时重复发出警报 | 只对新故障或故障集合变化播报；解除后允许未来同类新事件再报；`WAITING_CEO` 不算错误 | 单次故障只报一次、重新采样不反复报、`DETECTED` 和 `CLEARED` 均留档 |
| 06 | 首次重新启动中文监控窗口被误报失败 | 现场脚本生成的 `Start-Process` 参数引号有误，短暂进程退出。保留初次 `viewer_restarted=false` 回执；改用已核验的正确启动参数并按PID核对 | 后续窗口进程实际存活且仅1个，最终复核文件独立留存 |
| 07 | Windows PowerShell 5.1 执行中文UTF-8文件出现乱码或解析失败 | Windows PowerShell 5.1默认文本编码处理不同；中文脚本优先 PowerShell 7 `pwsh.exe -File`，不要误把编码错误当业务逻辑故障 | 编译解析正常、窗口中文可读、模拟故障类型中文可读 |
| 08 | PowerShell 中赋值 `$home` 导致异常 | `$HOME` 是自动只读变量；依照成熟 PowerShell 约束改用 `$grafanaRoot` | 修复最小变量名冲突，原安装逻辑可执行；不扩展修改范围 |
| 09 | GitHub技能包第一次写入中文损坏 | V008历史发生过文本传输编码失真；新文件使用官方Contents接口写入并**立即精确fetch_file回读**，字符串内容相等且Blob SHA正常方能改动正式索引 | 不只看提交成功，比较整文内容＋关键字段，失败拒绝升级指针 |
| 10 | 盲将8–10个执行器全开，系统反而变慢 | i5-3570实测原生运行空间优于短任务独立进程；初始2本地／4等待，按净收益扩容，不把“十方向”等于“十个Codex” | 等合同有效完成时间、错误恢复成本、资源与最终成果齐备 |
| 11 | 将 `READY`／`WAITING_CEO`／`BLOCKED` 视为故障或已经执行 | READY待授权；WAITING_CEO正常审批；BLOCKED是已知依赖阻塞，需授权解除。真实报警以 `alert_keys`、过期采样和状态文件失败为准 | 业务状态和监控异常各自可见，不盲启动／盲重试 |
| 12 | n8n health200但管理API401、Docker权限拒绝 | 健康接口只说明服务有响应；工作流管理及容器访问另需合法授权。复用 n8n 指挥台技能包1.0.2的既有修复记录、不要绕过授权 | 合法入口＋真实Webhook／业务回执＋独立审查，不能凭200认定通过 |
| 13 | 仅凭重启后无当前报警便宣称完整自愈 | 清除只是当前状态；必须保存先前故障记录、根因、影响范围、修复行动、结果对账和独立校验 | `DETECTED→已授权恢复→CLEARED→回执` 全链路，生产未知结果不重复提交 |
| 14 | 新业务升级V009后沿用旧V008固定SHA检查 | 现有采集器含V008特定Freeze与Manifest SHA校验，动态适配尚未测试 | 有效新冻结后经CEO独立批准最小适配、重新校验新哈希、模拟故障与清除，再更新认证范围 |
| 15 | 因精简显示而连历史完整监控能力也删除 | 保留Grafana软件目录、22项归档工具、原仪表盘/数据库/插件、历史证据和恢复说明；只停进程与新版数据发布 | 能定位到归档清单及原软件，复用需要新授权和复验，禁止默认重装 |
| 16 | 认为换目录直接省磁盘/轻量一定多开1个任务 | 搬家只移路径、不省磁盘；停止Grafana减运行负担，但未做真实Codex加载的净收益竞速 | 区分磁盘和RAM；不作“必定能多派一任务”的未经实测结论 |

以上均为定位与操作经验；不从零造通用机制，优先调用成熟原生组件和已实测GOOD基线。只有在差分证明旧路线确实失效时才替换，未证明无效的原配置/方法要留备份。

## 三、下一阶段的固定可验收测试清单

1. **基础读取（只读）**：用 GitHub 精确读取方法索引、技能入口、CURRENT/VERSION/最后Freeze，并在 Windows 确认两者相符。读取失败就报告 UNKNOWN，不能凭先前快照断定正常。
2. **轻量监控实况**：原监控任务每60秒更新，状态中文，一小窗口即可看清；高级后台进程0；运行内存采样并记录测量时刻。
3. **隔离报警**：先确认当前报警为空、测试标志不存在，在获准隔离区域**仅一次**注入可逆故障；确认 `alert_keys` 变更、中文解释、提示音API、语音退出状态。
4. **去重和解除**：相同故障保持数次刷新不重复播报；解除测试标记，在 `finally` 重新采集；`DETECTED`／`CLEARED` 成对留存。用户现场确认是否听到声音。
5. **未知结果与权限**：人为模拟 UNKNOWN 只测试“拒绝重发/先对账”规则；不得向真实客户发送、付款、广告投放或操作生产系统。
6. **保存点保护**：核对旧Freeze SHA和Manifest，逐任务独立目录，监控不得改写；新Freeze要单独验证监控适配，不能因为V008通过就直接推断V009通过。
7. **真实模型并发净收益**：Codex官方1/2/3 Agent，相同合同各做公平对照，计入监控成本、质量、失败与整合耗时；净收益≤0时停止加并行。
8. **后续长稳与恢复**：任务停止、用户注销、采集器停止、断电、系统冷启动、72小时观察、GPT主动通知与合规自动接管，逐项获得真实证据后再认证。
9. **完整监控重启（仅获批时）**：原生产品完整备份读取→低资源条件判断→恢复必要数据发布→官方插件数据源测试→多节点真实告警/历史→无副作用的独立核验→可回退；不得只看HTTP200。

## 四、事件处理与升级模板

事件最少保存：`TASK_ID`、`NODE_ID`、时间、原始故障键、中文故障类型、影响范围、已知GOOD基线、新的BAD证据、FIRST_DELTA、候选成熟方案（最多3个）、权限结论、恢复动作、业务结果（DONE/FAILED/UNKNOWN）、SHA／回执、独立复核、冻结ID、新版本指针。只追加新证据，历史失败不能为“好看”而删除。

发生故障：优先现成修复→只允许已授权隔离自动恢复→在同一合规测试合同完成验证→更新故障技能知识。业务副作用未知则停止执行并对账，不能以告警已解除替代业务成功。

V5 本次更新只升方法／技能包的整数版本；引擎28、Windows业务运行器v3.1.0、V008母Freeze、n8n指挥台1.0.2均不升级、不改写。
