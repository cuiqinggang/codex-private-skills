## 1. 运行目标概览（What）

### 1.1 MVE0 要实现的效果（复述）

1. 用户打开一个网页（你的页面，不是 ChatGPT 官网）。
2. 网页下方有一个提问框，可以输入问题并点击“发送”。
3. 后端程序在一台机器上 **自动打开 GPT 官方网页**，
   用已经登录的账号替用户把问题输入并发送。
4. 等 GPT 官网回答出来后，后端抓取回答内容，
   把这段文字返回给前端网页。
5. 网页上显示：

   * 右侧：用户提问气泡
   * 左侧：GPT 官方回答气泡

### 1.2 三层结构（概念）

* **前端（Front-end Web）**：
  只负责 UI 显示和把问题发给后端。

* **后端服务（Node.js 服务）**：
  接收问题 → 调用 Playwright → 等待回答 → 返回结果。

* **Playwright + 浏览器（实际跑在后端机器上）**：
  远程控制“真正的浏览器窗口”，操作 GPT 官网。

## 2. 托管推荐模式（Where）

这一节只定义**推荐的部署模式**，具体实现可以放到以后。

### 2.1 推荐托管模式（长期目标）

> **前端 = 免费静态托管**
> **后端 = 国外 VPS 上的 Node.js + Playwright**

* 前端可选择：

  * GitHub Pages
  * Netlify
  * Vercel（静态站）
    用于托管 `index.html` / `chat.js` / `chat.css` 等静态文件。

* 后端：

  * 部署在一台 **国外 VPS**（例如新加坡、日本、美国等区域）：

    * 安装 Node.js 环境
    * 安装 Playwright 和浏览器
    * 常驻运行一个 Node.js 服务，提供 `/ask` 接口

前端通过 HTTPS 调用后端的 `/ask`，后端再通过 Playwright 操作 GPT 官网。

### 2.2 Phase 0 执行策略（先本机实验，再上 VPS）

为了降低难度，Phase 0 建议：

1. **第一阶段：只在本机跑通**

   * 后端 = 你自己电脑上的 Node.js + Playwright
   * 前端 = 本机打开一个 HTML 文件（或本机简易服务）
   * 确认“浏览器自动登录 GPT 官网并能问答”可行

2. **第二阶段：再迁移到国外 VPS**

   * 把本机的 Node.js + Playwright 配置复制到 VPS
   * 把前端静态网页托管到 GitHub Pages 等免费平台
   * 修改前端中 `/ask` 的地址指向 VPS

本 RUNBOOK 后续步骤默认采用这个“两步走策略”。

## 3. Phase 0 – 本机实验流程（Node.js + Playwright）

本章目标：

> 在你自己的电脑上，从零开始，搭出一个“最小实验环境”，
> 能让 Playwright 自动打开 GPT 官网并完成一次“提问→回答→读取文本”的流程。

### 3.1 准备环境（不写命令，只写检查点）

在一台电脑上（建议 Windows / macOS / 主流 Linux）：

1. 安装并确认：

   * 已安装 Node.js（任意稳定版本即可）
   * 能打开 GPT 官方网页，并可以手动登录 ChatGPT 账号
2. 需要：

   * 稳定的外网访问（能正常打开 chat.openai.com / chatgpt.com）
   * 对命令行不恐惧（后面执行少量命令）

**验证点：**

* 在普通浏览器里，你能手动打开 ChatGPT，并用自己账号正常聊天。

### 3.2 建立项目目录结构（伪结构）

在本机上，新建一个项目目录，例如：

```text
UltraFusion-MVE0/
│
├── backend/           ← Node.js + Playwright 后端（未来部署到 VPS 的部分）
│   ├── server.js      ← 后端主入口（概念，不写代码）
│   ├── GPTWebClient.js← 封装“打开 GPT 官网、发送问题、读取回答”的逻辑
│   └── storage/       ← 存放登录状态等（例如 storageState.json）
│
└── frontend/          ← 简单网页（以后可托管到 GitHub Pages 等）
    ├── index.html
    ├── chat.js
    └── chat.css
```

此处只定义结构，不要求立刻写内容。

### 3.3 第一次用 Playwright 打开 GPT 官网并登录（流程）

目标：

> 确保 Playwright 能在本机正常打开“带界面”的浏览器，
> 并在你的手动操作下完成一次 GPT 登录。

推荐步骤：

1. 在命令行启动一个 **Playwright 带界面的测试脚本**（后续开发者会写脚本）。
2. 脚本会：

   * 打开一个真实浏览器窗口（例如 Chromium）
   * 打开 GPT 官网登录页
3. 你在这个窗口里 **手动输入账号密码 / 2FA / 其它验证**，
   直到看到正常的 ChatGPT 聊天界面。
4. 这时，Playwright 脚本可以把当前会话的“登录状态”保存成一个文件
   （常见命名：`storage/storageState.json`）。

**关键点：**

* 登录的过程只需要做一次。
* 以后所有自动化会尽量复用这份“登录状态文件”，避免频繁登录。

### 3.4 保存登录状态（概念）

在 `backend/storage/` 目录下：

* 约定有一个“登录状态文件”，例如：
  `backend/storage/gpt_storage_state.json`

用途：

* 后端每次启动 Playwright 浏览器时：

  * 读取这个状态文件
  * 以“已经登录好”的身份打开 GPT 官网
* 避免每个请求都重新登录。

RUNBOOK 只要求记录这个约定，不要求实现细节。

### 3.5 设计“提问 → 回答”的核心流程（伪代码）

在后端中，`GPTWebClient` 模块的逻辑可以用伪代码表示：

```text
函数 AskGPT(问题Q):

  1. 启动（或复用）一个 Playwright 浏览器和页面
     - 使用 gpt_storage_state.json 加载登录状态
     - 确保当前页面处于 ChatGPT 对话界面

  2. 在页面中找到“输入框”元素
     - 清空输入框
     - 填入问题 Q

  3. 触发“发送”操作
     - 模拟按下 Enter 键
     或
     - 点击发送按钮

  4. 等待新的回答块出现
     - 可以通过观察页面中回答区域的元素变化
     - 或设置合理的超时时间（例如几十秒）

  5. 从页面中获取最新一条回答的纯文本内容
     - 去掉页面中的装饰、按钮、图标，只保留文字

  6. 将这段文字作为返回值，交给调用者（例如 server.js）

  返回：GPT官网的回答文本
```

在 `server.js` 中的伪流程：

```text
当收到 HTTP POST /ask 请求，Body 中包含问题Q时：

  1. 调用 GPTWebClient.AskGPT(Q)
  2. 等待 AskGPT 返回回答文本
  3. 将回答文本包装为 JSON 返回给前端
```

本 RUNBOOK 只规定**流程**，不写实现代码。

### 3.6 用本机模拟一次完整链路（本机前端 + 后端）

当后端基本就绪后，可以做一次最小验证：

1. 启动 Node.js 后端服务（例如监听本机某端口）。
2. 在浏览器中打开 `frontend/index.html`（直接双击或者用简单静态服务器）。
3. 在网页输入框中输入一个简单问题，例如：

   > “请你用一句话解释什么是 UltraFusion MVE0？”
4. 点击“发送”：

   * 前端发送 `POST /ask` 到 `http://localhost:XXXX/ask`
   * 后端通过 Playwright 在 GPT 官网提问
   * 获取回答后返回前端
   * 网页显示用户问题（右边气泡）和 GPT 回答（左边气泡）

如果能完成上述过程，说明 **MVE0 在本机实验环境已打通**。

## 4. Phase 1 – 托管模式升级路线（VPS + 免费前端托管）

本章只描述“部署方向”，具体命令和配置可以后续另写细化版 RUNBOOK。

### 4.1 前端托管（建议）

将 `frontend/` 目录中的文件（`index.html` / `chat.js` / `chat.css`）：

* 上传到任意静态网站托管平台，例如：

  * GitHub Pages
  * Netlify
  * Vercel（静态站模式）
* 目标：获得一个公网可访问的 URL，例如：
  `https://yourname.github.io/UltraFusion-MVE0/`

前端中的 `/ask` 地址需要根据后端部署情况进行修改（指向 VPS 域名）。

### 4.2 后端托管在国外 VPS（概念步骤）

1. 租用一台国外 VPS（例如新加坡/日本/美国）
2. 在 VPS 上：

   * 安装 Node.js
   * 安装 Playwright 及其依赖和浏览器
   * 把 `backend/` 目录部署上去
3. 重复一次“登录 GPT 官网 + 保存登录状态”的流程，只不过这次是在 VPS 上用 Playwright 打开浏览器。
4. 让 `server.js` 在 VPS 上常驻运行，监听一个端口（例如 3000/4000 等）。
5. 确保前端托管的网页可以通过公网访问 VPS 的 `/ask` 接口（注意防火墙、安全组等配置）。

### 4.3 域名与 HTTPS（可选）

* 短期内：可以直接使用 VPS 的 IP + 端口进行访问。
* 中期：可以绑定一个域名，例如 `api.ultrafusion.xxx`
* 通过常见方案（如反向代理 + 免费证书）为后端接口加上 HTTPS。

该部分不属于 MVE0 的“强制要求”，但属于后续产品化方向。

## 5. 故障排查 Checklist（简版）

如果在实验或部署中遇到问题，可以按以下顺序排查：

1. **GPT 官网能否在普通浏览器中正常打开并登录？**
2. **Playwright 能否在本机正常打开浏览器？**
3. **登录状态文件是否成功生成（例如 gpt_storage_state.json）？**
4. **AskGPT 流程中，是否能在页面中正确找到输入框和回答区域？**
5. **Node.js 后端是否正常监听端口、能处理 `/ask` 请求？**
6. **前端网页是否指向了正确的后端地址？**
7. **网络连通性：前端 → 后端 → GPT 官网 的路径是否通畅？**

此处只列出方向，具体错误信息可在未来版本中逐步丰富。
