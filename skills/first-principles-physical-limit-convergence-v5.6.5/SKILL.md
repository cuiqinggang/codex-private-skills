# 整体闭环极限短时间引擎 v5.6.5

唯一目标：T*=min(T_VALID)。

v5.6.5 只做一个定点修复：把时间模型和全部时间相关规则恢复为“为了极限整体效率而测量时间”，删除不必要的时间源/API/历史补齐约束。其他业务逻辑不变。

## 两类时间

### 1. 本轮流程效率：T_FLOW
回答：从这一次真实开始工作的地方，到当前关键节点/完成，一共用了多久。

固定字段：
- FLOW_START_STATE：本轮实际切入的状态。
- FLOW_START_TIME：本轮实际开始时间。
- STATE_TIME：当前关键节点真实时间。
- T_FLOW：FLOW_START_TIME → STATE_TIME 的本轮耗时。

规则：
- 从哪里真实开始，就从哪里记录。
- 不要求必须从状态10开始。
- 已完成、未实际经历的历史状态不补造时间，也不为补时间而重跑。
- 本轮起点一经建立不重置。
- 起止时间可比较时机械计算 T_FLOW；不能可靠比较时只显示未知，不伪造。

### 2. 被优化任务时间：T_VALID / T*
回答：最终有效方案完成目标本身需要多久。

- T_VALID：满足 VALID 条件的任务实际有效时间。
- T*：可比、有效候选中的最短 T_VALID。
- 局部步骤很快不等于整体更快；局部耗时只作诊断，不得冒充 T_VALID/T*。
- 只有任务有效性已经被相应 verifier / 证据确认，才允许确认数值 T_VALID。

## 关键节点时间

状态机保持：
10 → 20 → 30 → 40 → 100

状态机回答“做到哪一步”；时间回答“何时到这里、从本轮起点用了多久”。

只在真实关键节点记录时间，重点包括：
- 本轮实际开始；
- 状态转换；
- 虚实交接/收件；
- 执行与审核；
- FINAL_VALID / 状态100。

不要求给没有实际发生的历史节点补时间。

## 时间来源

合同只要求：真实、带时区、可比较。

具体计时 API 不是协议核心。单一 API 不可用不得阻塞业务状态推进。实现可使用更高精度计时作为内部增强，但不能让它成为流程许可证。

## 比较边界

- T_FLOW 比较时必须看 FLOW_START_STATE / 测量范围；不同起点不得假装是同一完整区间。
- T_VALID/T* 只在同一 VALID 规格和可比任务范围内比较。

## 显示

正式核心头保持三行：
【页面名｜任务名｜序号｜虚/实】

【时间｜本轮起点=状态@时间｜当前节点=状态@时间｜本轮已用(T_FLOW)=...｜T_VALID=...｜T*=...】

## 不变项

v5.6.5 不修改：
- 10→20→30→40→100 状态机；
- judge / TRANSITIONS 业务判断；
- 实体证据文件 + SHA256；
- DSE / 业务 Freeze；
- 共同工作区来源规则；
- 局部最小修复原则；
- Reality 最终仍由 GPT 审核后才能进入100。
