# 局部最小化修复规则（Local Minimal Repair Policy）

本文件是维护规则，不属于 v5.6.3 已认证运行时文件，不改变既有现实认证提交与结果。

## 核心原则

**哪里出问题，只改哪里。没有现实证据证明有问题的部分，一律不动。**

禁止因为局部失败而默认重新设计、重构或重跑整套系统。

## 固定修复流程

现实测试发现问题后，按以下顺序执行：

1. **定位最小根因**
   - 先把 FAIL 归并到最小实现点。
   - 区分“局部代码 bug”与“架构/状态机缺陷”。
   - 只有证据证明架构本身有问题，才允许扩大修改范围。

2. **冻结未受影响部分**
   - 已 PASS 的状态机、接口、交接、显示、证据体系、时间规则等默认冻结。
   - 不因一个局部 FAIL 顺手重写无关模块。

3. **实施最小补丁**
   - 只修改能直接消除已证实根因的最少代码/配置。
   - 不附带“顺便优化”“统一重构”“清理架构”等无关改动。

4. **先做定向测试**
   - 只重放导致失败的原始反例。
   - 加入必要的最小正例，防止误杀合法输入。
   - 定向测试 PASS 后再进入回归。

5. **只跑已有回归防倒退**
   - 优先复用现成回归集。
   - 目的只是确认原 PASS 没被最小补丁破坏。
   - 不因局部修复重新发明一套大规模测试体系。

6. **现实复验**
   - 现实环境只复验本次修复点 + 必要回归。
   - 若全部 PASS，立即 STOP。
   - 不继续为了“更完整”而扩大范围。

## 默认禁止

除非出现直接现实证据，否则不得：

- 重写状态机；
- 重构已通过模块；
- 新增平行 Gate；
- 改动已通过的交接流程；
- 改动已通过的显示结构；
- 改动已通过的证据体系；
- 扩大测试范围；
- 因局部 bug 重新从头走一遍完整设计流程。

## 版本规则

- 已有现实认证 FAIL 的冻结版本不得原地改写成成功版本。
- 可以升级补丁版本号，但**版本升级不等于系统重做**。
- 新补丁版应尽可能满足：

```text
新版本 = 上一版本 + 最小必要补丁
```

- 未受影响的文件默认字节级复用；确需改动时必须能指出对应现实失败证据。

## 测试规则

局部修复默认只允许三层测试：

```text
A. 原失败反例
B. 最小正例/边界例
C. 现有回归防倒退
```

三层全部 PASS 后即可进入现实复验；现实复验 PASS 后立即停止，不继续扩大。

该案例作为本规则的基准示例：
