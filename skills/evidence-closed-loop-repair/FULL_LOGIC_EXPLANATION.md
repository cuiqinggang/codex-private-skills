# 全量证据闭环修复：完整逻辑、试错过程与最终闭环

## 一、为什么要建立这个技能

很多修复失败并不是因为“完全没有修改”，而是因为修改只发生在局部：某个源文件改对了，派生文件没同步；工作目录改对了，最终压缩包还是旧的；正确词出现了，但错误词仍散落在脚本、报告和嵌套包里；验证脚本显示PASS，但验证脚本本身使用了错误标准。

这类问题最危险的地方在于：**过程看起来非常完整，报告也可能非常漂亮，但用户实际拿到的文件仍然错误。**

本技能来自 UltraFusion V9.1 中一次真实、反复失败的修复：第二路模型本应是 `Qwen（阿里千问）`，却被写成 `Grok/xAI`。这个修改表面只是一处模型名纠正，实际牵涉源提示词、装配命令、稳定母版、生成器、验证器、报告、网页、截图、独立压缩包和最终压缩包。

用户的核心判断非常准确：

> 没有列出足够证据证明确实改进了、确实做到了，就相当于没有做到。

因此，本技能把“完成”的定义从主观声明改成可审计的证据合同。

---

## 二、原始任务并不是简单替换

用户最初要求同时完成四件事：

1. B层和C层的第二模型从 Grok/xAI 改回 Qwen（阿里千问）；
2. 0号源模板、06—09命令、1号母版及所有压缩包同步；
3. 删除10号最终评比中模型无法自行知道的运行成本、调用次数等字段；
4. 审查D层是否真正输出独立、有修复价值的终审答案，而不是复制C_Fusion或只给评审意见。

所以正确任务类型是：

```text
跨源头、派生链、构建系统、验证系统和最终交付物的全局一致性修复
```

## 三、用户是如何一步步收紧验收标准的

### 阶段1：用户纠正业务事实

用户明确：

```text
错误：GPT / Grok / DeepSeek
正确：GPT / Qwen（阿里千问） / DeepSeek
```

并明确A层本身不需要固定模型，但B、C和后续继承位置必须同步。

当时的错误理解是把任务缩小成“改03、04中的几个标签”。

### 阶段2：用户下载后发现实际未改

第一次宣布完成后，用户亲自下载、解压，发现Grok仍在。用户要求：

```text
不要不检查就说改了；弄完以后反复检查几遍。
```

这一步暴露出：验收对象错了。检查的是中间工作目录或局部文件，而用户使用的是最终压缩包。

### 阶段3：再次声明通过，但最终包仍错误

后续虽然增加了“多轮扫描”“残留为0”等声明，用户再次下载仍看见Grok。

直接对最终ZIP和7z做法证解压后，当时记录到：

```text
Grok/xAI相关残留：99处
```

并发现更深的根因：

- 构建脚本会主动把阿里千问重新写成Grok；
- 验证脚本又把Grok当作预期正确结果；
- 因此错误生成器和错误验证器形成循环自证。

这不是“没有运行验证”，而是“验证了错误真值”。

### 阶段4：用户发现06—09没有同步

即使03、04局部修改，07、08、09等装配文件和1号母版仍可能保留旧值。

这说明：

```text
源文件正确 ≠ 派生文件正确
```

必须建立明确派生关系：

```text
06 = 01 + 02
07 = 01 + 03
08 = 01 + 04
09 = 01 + 05
```

修改源后必须重新装配，而不是相信已有派生文件会自动同步。

### 阶段5：用户要求把所有内容当成新文件重新检查

用户最终明确：

```text
不只是06—09，所有有可能存在的地方都要检查；
因为已经错了好几次，不能信任以前的检查结果；
要把它当成一套全新文件重新验收。
```

这一步把验收范围扩展到：

- 所有正文；
- 所有文件名和目录名；
- 所有源文件和派生文件；
- 0号和1号副本；
- 生成脚本和验证脚本；
- README、报告、网页；
- 截图；
- 独立ZIP/7z；
- 完整ZIP/7z；
- 嵌套压缩包。

这才形成真正闭环。

## 四、前几次失败的八个根因

### 1. 范围低估

把系统性修改理解为局部字符串替换，没有先画影响图。

### 2. 没有区分真源头与派生产物

手工修改派生文件只能暂时正确。只要生成器再运行，错误就会复发。

### 3. 构建脚本未修正

生成器仍包含错误映射，导致“修好—重建—再次变错”。

### 4. 验证器真值被污染

验证器从生成器读取同一替换表。两个程序可以彼此一致，却同时背离用户要求。

### 5. 只做正向验证

看到Qwen出现便认为完成，却没有证明Grok、xAI、格洛克和旧槽位全部为0。

### 6. 验证了错误对象

工作目录PASS不代表用户下载的ZIP/7z PASS。压缩动作可能取了旧目录、旧缓存或旧嵌套包。

### 7. 没有递归检查嵌套包

外层包正确，内部0号/1号独立压缩包仍可能是旧版。

### 8. 同名覆盖造成版本混淆

浏览器缓存、旧下载、旧解压目录和新文件同名，用户无法确认打开的是哪一版。

## 五、最终闭环为何比“再检查一次”可靠

### 1. 独立变更合同

先把用户要求写成机器可读合同。以合同为真值，不以构建脚本为真值。

示例：

```json
{
  "required": [{"pattern": "Qwen（阿里千问）", "min_count": 1}],
  "forbidden": [
    {"pattern": "Grok", "max_count": 0, "case_sensitive": false},
    {"pattern": "xAI", "max_count": 0, "case_sensitive": false},
    {"pattern": "格洛克", "max_count": 0}
  ]
}
```

### 2. 全量影响图

不是只记录“要改的文件”，还记录：

- 会重新生成错误的脚本；
- 会复制错误的同步器；
- 会证明错误的验证器；
- 会展示错误的报告和截图；
- 会保存旧版本的压缩包。

### 3. 修真源头并全量重建

修正源提示词和生成器后，重新装配全部派生文件，再同步母版和旁路产物。

### 4. 正向和负向双重证明

```text
Required = 100%
Forbidden = 0
```

只有两个条件同时成立才通过。

### 5. 独立验证器Good/Bad测试

验证器必须能够：

- 接受真正正确的样本；
- 拒绝“多数文件正确但一个派生物仍残留Grok”的样本；
- 拒绝“工作目录正确但最终ZIP仍旧”的样本。

坏样本如果也通过，说明验证器无效。

### 6. 最终包冷启动

重新生成压缩包后，在全新临时目录解压，不使用旧工作目录和缓存，再跑完整合同。

### 7. 递归压缩包检查

外层ZIP/7z和内部嵌套包都要验证。无法检查的格式必须写PENDING。

### 8. 证据矩阵

每个PASS必须绑定可复核证据：文件路径、行号、计数、哈希、字节比较、截图或日志。

## 六、为什么截图重要但不充分

截图能够证明：

- 用户肉眼看到的关键输入区和顺序；
- 最终报告页面显示的内容；
- 某个关键文件是否出现正确模型名。

截图不能证明：

- 数十个文件中旧值为0；
- 嵌套包没有旧版本；
- 0号和1号逐字节一致；
- 锁定核心文件未改变；
- 下一次构建不会再次引入错误。

所以完整证据组合是：

```text
机器递归扫描
+ 正向/负向计数
+ 哈希与字节比较
+ 最终包冷启动
+ 截图
+ 语义分析
```

## 七、D层为什么需要语义Gate

即使所有Grok都被改成Qwen，系统仍可能“字面正确、功能无效”。

D层必须满足：

1. 把C_Fusion视为未经证明的候选答案；
2. 重新核验事实、证据、逻辑、反例和不确定性；
3. 可以推翻、重组或必要时重写；
4. 发现的材料性问题必须落实到D_Final正文；
5. 不能只输出审查清单或评分；
6. D_Final必须脱离C_Fusion独立阅读；
7. 不得读取A_Initial；
8. 不得混入10号最终价值比较。

这些内容不能通过关键词扫描完全证明，需要人工或模型语义审查。静态规则通过后，真实执行效果仍标记：

```text
RUNTIME_VALIDATION_PENDING
```

## 八、证据等级与允许声明

### E0｜无证据

只有“我改了”“应该好了”。禁止发布。

### E1｜局部证据

展示一两个文件或截图。只能证明局部。

### E2｜工作目录证据

工作目录全量机器检查通过，但最终包未验证：

```text
WORKTREE_PASS_PACKAGE_PENDING
```

### E3｜最终交付物证据

最终ZIP/7z冷启动、递归扫描、哈希、镜像和截图全部通过：

```text
FINAL_ARTIFACT_EVIDENCE_PASS
```

### E4｜真实运行证据

真实模型、真实输入、真实操作端到端运行。只有E4才能证明答案质量、真实时间和商业收益。

```text
中文名称：全量证据闭环修复

量化指标：Forbidden=0；Required=100%；镜像字节一致=100%；锁定哈希不变；冷启动包验证=100%

是否执行：满足触发条件时强制执行
```

## 十、永久规则

> 不验证“做事过程看起来是否完成”，只验证用户最终拿到的文件是否被独立证据证明正确。

> 一个PASS必须同时回答：正确内容在哪里？错误内容是否为0？最终下载包是否重新解压验证？

> 验证器与生成器一致，不等于它们与用户要求一致。

> 无法证明的事项不是“可能完成”，而是 `PENDING`。
