# Hermes Feishu Bot Bridge Runbook

## 2026-05-25 Proven Path

The working bridge used Feishu official `lark-oapi` long connection:

- App: `爱马仕机器人`
- Event: `im.message.receive_v1`
- Target group: `爱马仕ai测试群`
- Chat ID observed: `oc_3f39754af456234fa1d4de77022ef059`
- Hermes API: `http://127.0.0.1:8642/v1/chat/completions`
- Model: `hermes-agent`

The bridge script:

1. Starts `lark.ws.Client`.
2. Registers `register_p2_im_message_receive_v1`.
3. Logs `event_received`.
4. For `请严格只回复：HERMES_FEISHU_OK`, replies with fixed `HERMES_FEISHU_OK`.
5. For ordinary `@爱马仕机器人 ...`, calls local Hermes and replies with the model output.
6. Ignores non-text and non-@ group messages.
7. Deduplicates repeat deliveries by `message_id`.

## Failure History

### Missing Group Message Scope

Symptom:

- WebSocket connected.
- Group @ message visible in Feishu client.
- No `event_received` in bridge log.
- `read_recent_group_messages.py` returned `code=230027`, `need scope: im:message.group_msg`.

Fix:

1. Add Feishu permission `im:message.group_msg`.
2. Republish app version if Feishu requires it.
3. Restart bridge.
4. Send a fresh group @ message; old messages are not replayed.

### Fixed Acceptance Mode Skips Ordinary Questions

Symptom:

- `event_received` appears.
- Log shows `event_skip reason=trigger_not_matched`.
- Group gets no reply for ordinary questions.

Fix:

- Add general `@爱马仕机器人` route to Hermes.
- Keep fixed `HERMES_FEISHU_OK` acceptance path.

### Duplicate Feishu Event Delivery

Symptom:

- Same Feishu `message_id` appears twice.
- Two `hermes_request` and two `reply_sent` entries for one user message.

Fix:

- Keep an in-memory 10-minute `message_id` dedup cache.
- Do not dedup by message text; users may intentionally send the same question twice.

### Feishu Mention Placeholder After External Member Changes

Symptom:

- Group membership changed, for example external people were invited and later removed.
- WebSocket is connected.
- `event_received` appears for a new group @ message.
- Log text starts with a placeholder such as `@_user_1 你好`.
- Log then shows `event_skip reason=bot_not_mentioned`.
- The group gets no reply.

Cause:

- Feishu may deliver the mention as a placeholder token such as `@_user_1`
  instead of plain `@爱马仕机器人`.
- Some events include `mentions` metadata that maps the placeholder to the bot
  name; some only expose the placeholder text.

Fix:

1. Make `extract_bot_question` parse all supported @ formats:
   - plain `@爱马仕机器人 ...`
   - HTML-like `<at ...>爱马仕机器人</at> ...`
   - placeholder plus `mentions` metadata
   - leading placeholder only, such as `@_user_1 ...`
2. Restart the bridge so the updated parser is loaded.
3. Send a fresh group @ message; old messages are not replayed.

Verification:

- Log contains `event_received ... text=@_user_1 ...`.
- Log then contains `hermes_request`.
- Log then contains `reply_sent`.
- User confirms the Feishu group shows a normal bot reply.

### Chinese Encoding In Ad Hoc Hermes Tests

Symptom:

- Direct PowerShell JSON POST causes Hermes to respond as if it saw question marks.

Fix:

- Use Python `requests` or JSON with Unicode escapes.
- Bridge uses `json.dumps(..., ensure_ascii=True)` when calling Hermes.

## Stop Conditions

Stop before:

- Printing App Secret.
- Posting raw WebSocket URL containing `access_key` or `ticket`.
- Deleting Hermes, Open WebUI, New API, Docker, WSL, scheduled tasks, or model pool files.
- Changing Feishu account/security settings beyond the explicit app permission/version task.
- Switching to public callback URL unless the user asks for it.
