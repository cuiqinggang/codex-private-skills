# 《AI 化组织》V4.0｜按任务规模最简执行（整数升级）
状态：新分级规则正式纳入技能包，阶段性版本发布；非整个系统成熟验收通过。V2/V3 已冻结规则不覆盖。

## 唯一目标与方法
第一性物理极限时间为锚：先确立同质量真实基线 T0、关键路径物理下界 Tphys，再广域检索既有成熟技能包/官方工具/现成成果；最多三条有价值成熟候选，比较、融合、对抗迭代、整体虚拟成熟，Freeze 后按必要性一次关键 Reality。所有新增工具、步骤和角色都必须证明预计完整 T_VALID 净收益，计入失败、恢复、对账、返工和验收。无法完整交付的路线不能凭局部快速结果判优。

## 任务规模分级（本次升级正式规则）
- 小任务：GPT 直接执行，既有工具按需调用；**不启用 CEO+GPT 执行者双页面模式**。
- 中等任务：GPT 自主从目标到成果、验收全程负责，按净收益调用已有成熟技能包、Codex/工具；**不启用 CEO+GPT 执行者双页面模式**。普通网页设计/编码/运行/测试原则上属于直接执行，不因步骤较多自动升级。
- 大型复杂任务：仅当确实存在独立可分派的大业务节点且虚拟成熟显示完整 T_VALID 净收益为正，才启用双 GPT：主页面 GPT CEO 负责合同、关键路径、限时、派发、对账和最终 QA；GPT 执行者只负责具体业务。大小本身不是启用的充分条件。
- 默认 GPT 自执行；不另造调度器、不无意义地增加层级。大型节点超时，主控先核外部副作用，确认旧执行代不能再提交后仅重发未完成节点；不要自动重复预约、付款等不可逆动作。
- 本规则不要求无人值守，不要求自动打开或控制另一个 GPT 页面；主页面人工/授权运行的成熟派发入口即可。没有真实接单 ACK，不可声称已自动续跑。

## 存储和终止约束
线上 GitHub 共同工作区优先、C:\AI\AIORG-Shared 为同步/故障回退；遇到拒绝先检查自身调用、查成熟官方操作，普通单通道故障不使主任务终止。
编号即续跑：收到 TASK_ID 读取有效回执后继续未完成业务，状态汇报与规则写入不算业务完成；外部副作用 UNKNOWN 先对账。只有全合同独立 QA 与完整 T_VALID 通过，才标记 TASK_COMPLETE。
Windows A→B→C，代理设置不变；继承三人行 V5、轻量状态 V3、既有 ECC/DSH、Windows 执行桥规则。

## 证据边界
已验证 Windows 子进程限时淘汰/重发及真实 Tymeslot 提交后中断→数据库对账→避免重复创建；Tymeslot A/B 限定业务 13/13。尚未验收全部 N004 合同、改期完整恢复和全任务 T_VALID，INC-002 OPEN。不要把阶段性发布说成完整业务成熟。

# 《AI 化组织》V3.0｜节点版本化＋独立C盘强备（候选）
状态：成熟化候选，禁止把虚拟故障模拟宣称为完整GPT网页端到端验收。
## 唯一执行机制
与V2.0使用同一套TASK_ID、节点合同、节点版本化、页面可替换执行、按需DSH与ECC恢复。《三人行》V5、轻量状态V3、Windows执行桥V12 A→B→C均继承。简单/普通/超级复杂不拆三套系统，仅节点数量、规模和调用专业执行者不同。
## 在线优先，C盘独立强备
在线GitHub工程工作区是权威版本维护/发布路径；C盘并行生成独立备份，不成为正常任务的完成屏障。不执行每节点双仓全文对账；只有恢复使用备份时验证有效版本。
保存指令需进入可靠的独立执行入口才可宣称已排队，发送意图≠成功备份。单边故障由既有恢复设施异步修复，状态不得假报双仓完成。在线主仓失败时，从最近可用的C盘确认版本继续，恢复在线后对账补同步。不可逆外部副作用UNKNOWN先对账。
## 性能裁决
主任务T_VALID计入所有真实主路径交接、资源争用、失败重试、恢复与验收，独立并行后台耗时不机械累加。正常路径预计接近V2；故障下依靠额外备份减少恢复成本，必须真实验证，不能用假设概率宣告胜出。
## 当前证据
V2连续两次Windows执行节点故障恢复PASS；V3 GitHub和C盘实际双仓写读PASS；单侧跳写后补写PASS；R7为全状态假设敏感性模拟，不是真实全部GPT页面故障测试。
## 尚未完成
连续真实GPT页面全部失效并由新GPT读取TASK_ID交付、独立守护自动唤起真实新执行实例、持久队列断电恢复、相同真实复杂业务V2/V3端到端T_VALID A/B。未过验收不冻结或替换V2。

## 默认 GPT 业务页面故障换页（继承 V2，人工实操成熟基线）
适用：当前 GPT 页面卡顿、失效、上下文过长或业务节点无法继续。
1. 保留原 TASK_ID / NODE_ID 与原始任务合同。能复制原页面有效上下文时直接复制；已归档成果不需要重新执行。
2. 从原页面或任务仓库整理最小恢复包：目标与约束、已完成节点及成果位置、最新有效版本、未完成节点、NEXT_ACTION。在线主仓优先；在线不可读取时使用 C 盘已保存版本。DSH仅在故障时协助整理状态、定位失败节点与核对成果，不参与正常业务。
3. 在新 GPT 业务页面粘贴恢复包或给出 TASK_ID 及仓库地址，要求读取已完成版本并继续未完成节点。此为故障页面的业务迁移；人工提交不等于无人值守自动投递，不要求凭空恢复故障页面的隐藏推理。
4. 新页面实际完成剩余业务并产生结果后，保存新的有效节点版本；在线优先，C盘独立非阻塞备份。确认可继续后再关闭旧页；旧页已经不可用则不依赖它。
5. 以原任务最终成果和 T_VALID 评价恢复效果，不把“新页面已打开”“恢复包已生成”误判为业务交付。若页面无法操作、仓库不可用或外部副作用 UNKNOWN，按既有 STOP_GATE 处理。
操作目标：沿用用户长期实际成功的“复制必要内容→新页面→任务ID读取→继续执行”，不新增调度器、浏览器控制器或逐节点双仓全文比对。
验收范围：这是一条明确的故障操作规程；是否能够在某次会话无人工提交下自动接续，必须另按可用执行入口判定，不作为该手动恢复路径的前置条件。
